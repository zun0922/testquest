## 1. ライブラリ選定

### 採用

| ライブラリ | 用途 | ライセンス | 採用根拠 |
|-----------|------|----------|---------|
| react / react-dom | UI | MIT | クロスワードで実績。技術スタック制約（要件8.1） |
| typescript | 型安全 | Apache-2.0 | 同上 |
| vite | ビルド | MIT | 同上 |
| tailwindcss | スタイリング | MIT | 同上 |
| @playwright/test | E2E | Apache-2.0 | クロスワードのテスト資産・ノウハウ流用（devDependency） |

### 不採用（検討の上見送り）

| 候補 | 用途 | 不採用の根拠 |
|------|------|------------|
| react-router | 画面遷移 | 画面は4つで遷移が線形（10章 状態遷移図のとおり）。URLによるディープリンクは進捗保存（localStorage）と整合せず、リロード時はタイトルに戻る仕様（要件10章）のため不要。画面enum＋state管理で実現する |
| zod 等のスキーマ検証ライブラリ | シナリオJSON検証 | 検証項目が限定的（3.4の12項目）で自前関数により依存を増やさず実現可能。クロスワードの csvLoader.ts 方式を踏襲する |
| zustand / redux 等の状態管理 | 状態管理 | 画面4つ・状態の所有者が単一フック（useGame）で完結する規模。React組み込みの useReducer で十分（software-design.skill §6 準拠） |
| ノベルゲームエンジン（Ren'Py・TyranoScript・Monogatari等） | シナリオ再生 | 下表の比較により現スコープでは自前実装を採用。エンジン側も変数・分岐・セーブは持つため「機能不足」が理由ではなく、本作固有の条件（既存React資産の流用・独自UI/データ要件・テスト容易性）で自前が有利と判断した。詳細は下記 |

#### ノベルゲームエンジン非採用の詳細根拠

エンジン（Ren'Py・TyranoScript・Monogatari 等）は変数・フラグ分岐・セーブ・立ち絵切替を標準で備えており、機能面では本作のシナリオ再生を実現できる。それでも現スコープで自前実装を選ぶ理由は以下の比較による。

| 観点 | エンジン採用時 | React自前実装 |
|------|--------------|--------------|
| 既存資産の流用 | 独自スクリプト言語＋別ランタイム。クロスワードの React/Vite/Playwright/CI・引き継いだルール/スキル・data-testid方式のE2Eがほぼ活かせない | 同一構成でそのまま流用できる |
| 独自UI/データ要件 | 数値非表示メーター（UI-RULE-006）・評価3段階・参照シラバス項番表示・採用導線データは、エンジン標準UIの上書き／拡張になる | 要件どおり直接実装できる |
| テスト容易性 | エンジン内部状態の検証手段が限られる（localStorage直読・data-testid が使いにくい） | AC-006の内部値検証（localStorage直読）をそのまま記述できる |
| 学習特化の拡張 | AL解放ロジック・プレイ結果送信は学習アプリ固有でエンジンの想定外 | アプリの一部として自然に実装 |
| ライセンス・保守 | エンジンごとにライセンス・メンテ状況の確認コストが発生（TyranoScript等は要確認） | 新規依存ゼロで確認不要 |

> **判断の射程：** これは「Phase 1規模（画面4つ・線形遷移・浅い分岐）では自前で十分」という判断でもある。AL編で演出（立ち絵アニメ・音声・複雑分岐）を本格化させる場合は、その時点でエンジン採用を再評価する（恒久的な不採用ではない）。

> 新規の外部依存はゼロ（クロスワードと同一構成のみ）。ライブラリ追加が発生する場合は LICENSES.md へ追記し人間承認を得る（`.claude/rules/common/workflow/licensing-policy.md`）。

## 3. データ構造定義

### 3.1 基本型

```typescript
export type StatusKey = 'knowledge' | 'skill' | 'confidence' | 'teamwork';
export type StatusValues = Record<StatusKey, number>;   // 各 0〜100 の整数

export const INITIAL_STATUS: StatusValues = {
  knowledge: 10, skill: 10, confidence: 10, teamwork: 10,   // 要件 FR-006
};

export type Rating = 'best' | 'good' | 'poor';   // 最適／可／要改善（FR-005）

export type CharacterId = 'rin' | 'tanaka' | 'ken';
export type Expression = 'normal' | 'happy' | 'angry' | 'sad' | 'thinking';
export type Position = 'left' | 'right';
```

### 3.2 シナリオデータ（JSON）

```typescript
// public/data/scenarios/index.json
export interface ScenarioIndex {
  version: 1;
  scenarios: ScenarioIndexEntry[];
}
export interface ScenarioIndexEntry {
  id: string;                 // 'fl-1-01' 形式（要件6.1）
  title: string;
  level: 'FL';                // Phase 3 で 'AL-TM' | 'AL-TTA' を追加
  chapter: number;            // 1〜6
  order: number;              // 章内の表示順（FR-002 は order 昇順）
  estimatedMinutes: number;   // 所要時間目安の表示用
  file: string;               // 'fl-1/fl-1-01.json'
}

// 各シナリオファイル
export interface Scenario {
  id: string;
  title: string;
  startNodeId: string;
  nodes: SceneNode[];
}

export type SceneNode = TextNode | ChoiceNode;

interface NodeBase {
  id: string;
  background: string;               // 'office' 等（images/backgrounds/ のファイル名）
  characters: CharacterDisplay[];   // 0〜2体（UI-RULE-004）
  speaker: CharacterId | 'narration';
  text: string;                     // 最大200文字（UI-RULE-002）
}
export interface TextNode extends NodeBase {
  type: 'text';
  next: string | null;              // null＝最終シーン（結果画面へ）
}
export interface ChoiceNode extends NodeBase {
  type: 'choice';
  choices: Choice[];                // 2〜3個（UI-RULE-003）
}

export interface CharacterDisplay {
  characterId: CharacterId;
  expression: Expression;
  position: Position;               // 同一 position の重複は検証エラー
}

export interface Choice {
  text: string;                       // 最大40文字
  rating: Rating;
  statusEffects: Partial<Record<StatusKey, number>>;  // 値は1〜5・1キー以上必須（減算なし）
  feedback: Feedback;
  next: string;                       // 分岐先ノードID
}

export interface Feedback {
  explanation: string;     // 最大400文字
  syllabusRefs: string[];  // 例 ['1.3']。1件以上必須（FL V4.0 項番）
}
```

### 3.3 進捗データ（localStorage）

- キー名：`testquest:save`（E2Eテスト・機能テストでの内部値検証はこのキーを読む。AC-006）
- 値：以下を `JSON.stringify` した文字列

```typescript
export interface SaveDataV1 {
  version: 1;                       // スキーマバージョン（FR-008）
  status: StatusValues;
  cleared: Record<string, ClearRecord>;   // key＝シナリオID
}
export interface ClearRecord {
  clearedAt: string;                // ISO 8601
  ratings: Record<Rating, number>;  // 初回クリア時の評価内訳
  statusGain: Partial<Record<StatusKey, number>>;  // 初回クリア時の合計変動
}
```

### 3.2.4 編成パターンのデータ（FR-P2-003・Phase 2）

`public/data/casting.json`。**シナリオJSON 71本は変更しない**のが設計の要。

```
{ "version": 1, "castings": [
    { "id": "default", "label": "高橋 匠", "swap": {}, "textOverrides": {} },
    { "id": "mio", "label": "伊藤 澪", "swap": { "takumi": "mio" },
      "textOverrides": { "al-tta-1-01": { "intro": "..." } } } ] }
```

- **`swap`**：話者IDと立ち絵のキャラIDを表示時に読み替える。位置・表情はそのまま
- **`textOverrides`**：一人称・二人称・名乗りだけを直した本文の差分。**7か所のみ**
  （匠のセリフ144本のうち男性寄りの表現を含むのは5%・名乗りは全71本で1か所だけという実測に基づく）
- 選択は `testquest:ui` の `casting`（進捗とは別キー）。定義が読めなければ既定の編成で従来どおり動く
- **音声**は差し替えたキャラのぶんだけ `public/audio/{編成ID}/{scenarioId}/{nodeId}.m4a` に置き、
  `manifest.variants[編成ID]` に登録する。**既定の音声（26MB）には触れない**ので、
  パターンを増やしても増えるのは差し替えたキャラのぶん（澪は144ノード・6.0MB）だけで済む

### 3.2.3 既読の記録（FR-P2-005・Phase 2）

`localStorage` の **`testquest:read`**（進捗の `testquest:save` とは別キー）。

```
{ "version": 1, "nodes": { "fl-1-01": ["n1", "n2", ...] } }
```

- **別キーにする理由**：既読は利便性のための補助データであり、壊れても**学習の進捗を失ってはならない**。
  読めないときは「未読」として扱えば、従来どおり遊べる（`loadReadLog()` は例外を投げず空を返す）
- **ノード単位にする理由**：シナリオ単位だと、分岐のあるシナリオで**通っていない枝まで既読扱い**になる
- 保存に失敗（容量超過・プライベートモード）しても、その場の記録は返すのでセッション中はスキップが効く

### 3.2.2 エンディングのデータ（FR-P2-002・Phase 2）

`public/data/endings.json` に全7種を1ファイルで持つ（シナリオと違い件数が少ないため）。
1行は `speaker` / `characters` / `text` を持ち、**シナリオのノードと同じ構成部品**にして描画を流用する。

進捗側は `SaveData` を2箇所拡張した（**いずれも省略可＝既存セーブと後方互換**）。

| フィールド | 用途 |
|-----------|------|
| `ClearRecord.cleanGain` | **poor を除いた**シナリオごとの成長。エンディング判定に使う |
| `SaveData.endings` | 到達したエンディングID → 到達日時。一覧と再生に使う |

`cleanGain` を `statusGain` と分けるのは、**poor でも知識が大量に入る**構造のため。
分けないとどのプレイでも知識が突出し、エンディングが分岐しない（`docs/エンディング機能_要件仕様_v0.1.md` §1.3）。

### 3.3.0 ヒントのデータ（FR-P2-007・Phase 2）

`ChoiceNode` に **`hint?: string`**（最大100字・validator **#14**）を追加した。**答えを言わず考える観点だけ**を示す1〜2文で、
ヒントの主役はこちら。書き方のガイドラインは `docs/ヒント機能_要件仕様_v0.1.md` §4.2。


`Choice` に **`emphasis?: string[]`** を追加した（省略可）。ヒントで強調する語を `text` 内の部分文字列で指定する。

```jsonc
{
  "text": "動的に実行して欠陥を探すこと",
  "rating": "good",
  "emphasis": ["動的に実行"],   // 追加（省略可・最大2語＝LIMITS.EMPHASIS_MAX）
  ...
}
```

- **`text` は変更しない**。本文にマークアップを埋め込まず別フィールドに持つことで、監修済みの文面を不変に保つ
- **省略可**とすることで章単位の段階導入ができる（データの無い問題ではヒントを出さない）
- validator **#13** で「指定語が `text` に実在する／範囲が重ならない／最大2語」を検証する。
  指定語が本文に無いと「押しても何も起きない」空振りになるため、門番テストで全数検出する

### 3.3.1 音声マニフェスト（FR-P2-006・Phase 2）

音声ファイルのパスは**規約で決まる**ため、シナリオJSON（監修済み71本）には手を入れない。
存在判定に毎回 404 を出さないよう、索引を `public/audio/manifest.json` に置く。

```jsonc
{
  "version": 1,
  "format": "m4a",            // AAC。Ogg Opus は iOS 16 以前の Safari が再生できないため
  "scenarios": {
    "fl-1-01": {
      "n1": { "hash": "a3f...", "dur": 8.2, "cast": "tanaka" }   // hash＝読み上げテキストのSHA-256
    }
  }
}
```

- 配置：`public/audio/{scenarioId}/{nodeId}.m4a`
- `hash` は**差分再生成**の判定に使う（テキストや配役パラメータを変えたノードだけ鳴らし直す）
- シナリオと音声の食い違い（未生成・置き去り・配役の取り違え）は門番テスト `voice.data.test.ts` が検出する

### 3.4 シナリオ検証ルール（validator.ts・FR-009）

ロード時に以下を検証する。1件でも違反があれば `ValidationError`（違反内容の配列を保持）とし、当該シナリオを開始しない。

| # | 検証項目 | 種別 |
|---|---------|------|
| 1 | 必須フィールドの存在・型一致 | エラー |
| 2 | ノードIDの一意性 | エラー |
| 3 | `startNodeId`・各 `next` の参照先ノードが存在する | エラー |
| 4 | 選択肢数が2〜3 | エラー |
| 5 | `text` ≦200文字・`choice.text` ≦40文字・`explanation` ≦400文字 | エラー |
| 6 | `statusEffects` が1キー以上・各値が整数1〜5 | エラー |
| 7 | `syllabusRefs` が1件以上 | エラー |
| 8 | `characters` が0〜2体・`position` 重複なし | エラー |
| 9 | `speaker` が `characters` に存在するか `narration` | エラー |
| 10 | 選択肢ノード数が3〜5（要件6.1） | エラー |
| 11 | `startNodeId` から到達不能なノードの存在 | 警告（`console.warn`・開始は許可） |
| 12 | 最終ノード（`next: null`）が1つ以上存在する | エラー |

> 到達不能ノード（#11）を警告に留める根拠：分岐の編集途中で一時的に発生しやすく、プレイ自体は破綻しないため。データ制作のLayer 1チェック（AI生成時）で検出・解消する。

## 5. 機能別処理フロー

### 5.0 アプリ起動

```
main.tsx → App マウント
  → storage.isAvailable() で localStorage 使用可否を判定（try { setItem/removeItem } catch）
  → scenarioLoader.loadIndex()（fetch public/data/scenarios/index.json）
      ├─ 成功＋検証OK → タイトル画面表示（hasSave＝storage.load() の有無）
      └─ 失敗 → ErrorScreen（5.9）
```

### 5.1 FR-001　タイトル画面

```
「はじめから」クリック
  ├─ セーブなし → dispatch(START_NEW) → 進捗を INITIAL_STATUS で初期化 → SelectScreen
  └─ セーブあり → ConfirmDialog「進捗が削除されます」
        ├─ OK → storage.clear() → START_NEW
        └─ キャンセル → 閉じる（タイトルに留まる）
「つづきから」クリック（セーブなし時は Button disabled）
  → storage.load() → 復元 → dispatch(CONTINUE) → SelectScreen
  → 読み込んだ JSON が SaveDataV1 として不正（version 不一致・型不正）の場合：
     console.error 出力＋「保存データが読み込めませんでした」を表示し「はじめから」のみ活性化（セーブは消さない）
localStorage 使用不可時：タイトル画面に注意文「この環境では進捗が保存されません」を常時表示（FR-008）
```

### 5.2 FR-002　章・シナリオ選択（v1.2：レベル別セクション／v1.4：折り畳み）

```
表示時：LEVELS（FL / AL-TM / AL-TTA・src/utils/levels.ts が正）ごとにセクション表示
  ├─ 各セクション内は index.json の scenarios を level→chapter でグループ・order 昇順
  ├─ シナリオが存在する章 → 活性（タイトル・クリア済みバッジ・所要時間目安）
  ├─ シナリオが無い章 → 非活性カード「第n章 <章題>（制作中）」（UI-RULE-001）
  └─ ALセクションはロック判定：
       isAlUnlocked ＝ index 上の FL 全シナリオが save.cleared に存在（企画書§5.5・levels.ts）
       ├─ 未解放 → 🔒カード「Foundation Level の全章クリアで解放されます」
       └─ 開発・テスト用フック ?unlockAll=1（import.meta.env.DEV 限定・本番ビルド無効＝テストデータ原則）
シナリオクリック → dispatch(SELECT_SCENARIO) → scenarioLoader.loadScenario(file)
  ├─ 成功＋検証OK → ScenarioPlayer（startNodeId から再生・isReplay＝cleared に存在するか）
  └─ 失敗 → ErrorScreen（進捗は変更しない）
```

- 章タイトルの正：FL＝FLシラバスV4.0章題／AL＝企画書§5.2.1・§5.3.1（`levels.ts` の titles）
- v1.0 の記述（chapter 1 のみ活性・2〜6 は「Phase 2で追加予定」）は FL全章完成（2026-07-03）と AL 追加により本節へ置換

**折り畳み（v1.4・全71本でのスクロール量過大の対処。PO要望 2026-07-25）**

```
レベル見出し・章見出しをトグルボタン化（aria-expanded／閉じている節は中身を描画しない）
  ├─ 開閉判定：isOpen(key) ＝ overrides[key] ?? 自動判定
  │    ├─ overrides ＝ ユーザーが明示的に開閉した節のみ（utils/uiState.ts・localStorage 'testquest:ui'）
  │    └─ 自動判定 ＝ 「続きの章」とその親レベルだけ開く（findContinueChapter・levels.ts）
  │         続きの章 ＝ 未クリアが残る最初の章（LEVELS順→章番号順・ロック中のALは対象外）
  │         全クリア時（続きなし）＝ 先頭レベル（FL）の見出しのみ開く
  ├─ 見出しにクリア進捗を表示：レベル「n/N クリア」・章「n/N」（完了章は「✓ N/N」）
  │    ※ UI-RULE-006（ステータスの数値非表示）の対象外＝学習進捗の件数表示
  └─ 開閉状態の保存は SaveDataV1 と別キー（進捗データ・マイグレーションに影響しない）
       保存失敗（Quota・利用不可環境）は無視する＝自動判定で表示は成立する
```

- 明示操作が自動判定に優先する（例：続きの章を畳んだら畳まれたまま）。未操作の節は進捗に応じて自動で開くため、章を進めると展開先も追随する
- AL解放直後は「続きの章」が AL-TM 第1章になるため、FL は自動的に畳まれた状態で AL が開く

### 5.3 FR-003　シナリオ再生（テキスト送り）

```
ノード表示 → useTypewriter が text を30ms/文字で送り表示
  ├─ 送り中にクリック → 全文即時表示（typing → done）
  └─ done 状態でクリック
        ├─ type==='text' かつ next!==null → dispatch(ADVANCE) → 次ノード
        ├─ type==='text' かつ next===null → dispatch(FINISH) → 結果画面（5.7）
        └─ type==='choice' → クリックでは進まない（選択待ち。ChoiceOverlay 表示中）
PauseMenu「シナリオを中断」 → ConfirmDialog → OK → dispatch(QUIT) → SelectScreen
  （途中状態は破棄。進捗＝status/cleared はシナリオ開始前のまま）
```

- 立ち絵：`node.characters` を描画し、`speaker` 以外は `grayscale(1) brightness(.45)`（モックA案準拠）
- 話者名：`speaker==='narration'` のときは話者名チップを非表示にし、本文のみ表示する

#### キャラクターボイス（FR-P2-006・Phase 2）

```
ノード表示 → useVoice が manifest を引き、音声があれば同時に再生（テキスト送りとは同期しない）
  ├─ 送り中にクリック → 全文即時表示。音声は鳴り続ける（セリフを最後まで聞ける）
  ├─ done 状態でクリック → 次ノードへ。前ノードの音声は停止し、新しい音声を再生
  └─ 音声なし／設定OFF／再生拒否 → 無音のまま従来どおり進行（プレイを止めない）
```

- 音声要素は**アプリ全体で単一インスタンス**（`voice.getSharedAudio()`）。同時に2つのセリフが鳴るのを構造的に防ぎ、
  iOS Safari の「操作起因で一度 play() した要素しか後から鳴らせない」制約に対応する
- 自動再生ポリシー対策として、最初の `pointerdown` で無音を一瞬再生して解錠する（`App.tsx`）
- 再生状態は `screen-play` の `data-voice-state` 属性（`off`／`none`／`playing`／`blocked`）で観測できる（E2E用）
- ON/OFF は `testquest:ui`（進捗とは別キー）に保存する。音量は同キーに持つが UI は現状 ON/OFF のみ

### 5.4 FR-004　選択肢と分岐

```
choice ノードで本文表示完了 → ChoiceOverlay 表示（定義順・UI-RULE-003）
選択肢クリック → dispatch(CHOOSE, index)
  reducer 内：
    1. isReplay でなければ pendingEffects＝choice.statusEffects を status に加算（status.ts: clamp 0..100）
       isReplay なら status は変更せず表示用の差分のみ保持（FR-002 再プレイ仕様）
    2. ratings[choice.rating] をインクリメント（当該プレイのみのカウンタ）
    3. FeedbackModal を表示状態にする
FeedbackModal「閉じて次へ」 → dispatch(CLOSE_FEEDBACK) → choice.next のノードへ
```

#### ヒント（FR-P2-007・Phase 2）

```
ChoiceOverlay 描画時 → hintLevel(status, session.level) でヒントの強さを判定
  Lv0（閾値未満）／ヒント文も強調データも無い問題 → ボタンは非活性（押せない）
  Lv1 以上 → 「ヒントを見る」ボタンが活性
      押下 → Lv1：node.hint（ヒント文）を選択肢の上に表示
             Lv2：ヒント文に加え、emphasizedIndices() が返す全選択肢を強調
                  splitByEmphasis() が text を分割し、該当断片を <strong class="text-hint"> で描画
選択肢を選ぶ → 次の問題では key={node.id} により ChoiceOverlay が作り直され、表示状態はリセット
```

- **閾値はレベル別**（`utils/hint.ts` の `HINT_THRESHOLDS`）：FL は 60/150、AL-TM・AL-TTA は 170/300。
  同じセーブでも「FL の問題では出て AL の問題では出ない」状態が起こりうる（上級ほど自力で考えさせる設計）
- **ヒント文が主役**（何を考えるか）、**強調は補助**（それが選択肢のどこにあるか）。STEP 2 のPO確認を受けた構成
- 特定の選択肢だけを光らせると正解が割れるため、Lv2 では**全選択肢**を強調する
- **数値は一切表示しない**（UI-RULE-006）。ボタンの活性/非活性でポイントの育ち具合が間接的に伝わる
- 判定に使うレベルは `PlaySession.level`（`SCENARIO_LOADED` 時に index の entry から渡す）
- 詳細要件の正は `docs/ヒント機能_要件仕様_v0.1.md`（v0.2）

### 5.5 FR-005　フィードバック表示

- 表示内容：評価バッジ（rating→ 最適＝`rating-best`色／可＝`rating-good`／要改善＝`rating-poor`）・explanation・syllabusRefs（`FL {ref}` 形式で表示）・成長表示（5.6）
- 閉じる手段は「閉じて次へ」ボタンのみ（オーバーレイクリックでは閉じない。誤タップで解説を読み飛ばすことを防ぐ）

### 5.6 FR-006　ステータス成長表示

- FeedbackModal 内：変動した statusKey ごとにミニメーターを表示。既存値（status色）＋増加分（`status-gain`色・点滅アニメーション）の2層バー。数値テキストなし（UI-RULE-006）
- 再プレイ時：ミニメーター自体を表示せず「クリア済みシナリオのため成長は加算されません」の注記を表示する

### 5.7 FR-007　シナリオ結果表示

```
FINISH 時：
  1. 当該プレイの集計（ratings・statusGain＝選択ごとの効果の合計）
  2. isReplay でなければ cleared[scenarioId] に ClearRecord を記録し storage.save()
     （保存失敗＝QuotaExceeded 等は console.error＋画面に「進捗の保存に失敗しました」注記。結果表示は継続）
  3. ResultScreen 表示：タイトル・評価内訳（最適/可/要改善の個数）・StatusHud(compare)
     でプレイ前→後を表示・参照した syllabusRefs の重複排除リスト
「章選択へ戻る」 → SelectScreen
```

### 5.8 FR-008　進捗保存（storage.ts）

| 関数 | 仕様 |
|------|------|
| `isAvailable()` | try/catch で setItem/removeItem を試行。起動時に1回判定し結果を state に保持 |
| `load()` | キー `testquest:save` を parse。型ガード `isSaveDataV1()` で検証。不正なら `null` を返し console.error |
| `save(data)` | stringify して setItem。例外は呼び出し側へ throw（5.7 参照） |
| `clear()` | removeItem |

- 保存タイミングは結果画面表示時のみ（FR-008。オートセーブなし）
- 将来の `version: 2` への移行関数の置き場所（`migrate()`）だけ用意し、MVPでは恒等処理とする

### 5.9 FR-009　ロードエラー（ErrorScreen）

- 表示：「シナリオデータの読み込みに失敗しました」＋「再読み込み」ボタン（クリックで同じ fetch を再実行。リトライ回数の上限は設けない＝ユーザー操作起点のため無限ループにならない）
- 開発者向け：console.error に URL・HTTPステータス・ValidationError の違反一覧を出力
- 検証エラーの違反内容はユーザー画面に表示しない（要件 FR-009「技術詳細を表示しない」）

## 6. 状態管理設計

### 状態の所有者

| 状態 | 型 | 所有者 |
|------|----|--------|
| 現在の画面 | `'title' \| 'select' \| 'play' \| 'result'` | useGame（useReducer） |
| ステータス・クリア状況 | `SaveDataV1` 相当 | useGame |
| 現在のシナリオ・ノードID・ratings カウンタ・isReplay | `PlaySession \| null` | useGame |
| フィードバック表示中の choice | `Choice \| null` | useGame |
| インデックス・シナリオのロード状態 | `'loading' \| 'success' \| 'error'` | useGame |
| localStorage 使用可否 | `boolean` | useGame（起動時に確定） |
| テキスト送りの進行（表示文字数・typing/done） | number ほか | useTypewriter（ScenarioPlayer ローカル） |
| ダイアログ・メニューの開閉 | boolean | 各コンポーネントのローカル state |

### データフロー概略

```
index.json ─→ scenarioLoader ─→ useGame.state.index
scenario JSON ─→ validator ─→ useGame.state.session（再生中のみ）
useGame.state.save ←→ storage.ts ←→ localStorage('testquest:save')
選択 → reducer(CHOOSE) → status.ts（加算・クランプ）→ state 更新 → StatusHud 再描画
```

- reducer は純粋関数とし、localStorage への書き込みは結果画面遷移時に副作用として App 層で実行する（`.claude/rules/common/react/state-side-effects.md` 準拠）

### 8.4 レイアウト詳細仕様の先行策定（必須・開発フロー定義 STEP 2 準拠）

## 10. E2Eテスト自動化方針

### 10.1 方針

- クロスワードの Playwright 構成（localhost／Vercel の2モード・GitHub Actions CI）を踏襲する
- テスト仕様書・手順書の作成は次工程（テスト計画書承認後）。本章は実装が備えるべきテスト容易性のみ定義する

### 10.2 data-testid 設計

| testid | 要素 |
|--------|------|
| `screen-title` / `screen-select` / `screen-play` / `screen-result` / `screen-error` | 各画面ルート |
| `btn-start` / `btn-continue` | タイトルのボタン |
| `scenario-item-{id}` | シナリオカード（例 `scenario-item-fl-1-01`・`scenario-item-al-tm-1-01`） |
| `chapter-{n}` | FL の章グループ（既存E2E・スクショとの互換のため FL は接頭辞なしを維持） |
| `level-{slug}` / `chapter-{slug}-{n}` / `lock-{slug}` | v1.2 追加：レベルセクション・ALの章グループ・ALロックカード（slug＝`al-tm`/`al-tta`） |
| `level-toggle-{slug}` / `chapter-toggle-{slug}-{n}` | v1.4 追加：折り畳みの開閉ボタン（`aria-expanded` を持つ。slug＝`fl`/`al-tm`/`al-tta`・章は全レベルで slug 付き） |
| `message-window` / `speaker-name` | メッセージウィンドウ・話者名 |
| `choice-btn-{n}` | 選択肢（n=0..2・定義順） |
| `feedback-modal` / `feedback-rating` / `btn-feedback-close` | フィードバック |
| `status-bar-{key}` | メーター（key=knowledge 等。`aria-valuenow` は付与しない＝数値非表示の徹底） |
| `btn-pause` / `btn-quit-confirm` | 中断メニュー |
| `btn-back-select` | 結果画面の戻るボタン |

### 10.3 内部値の検証方法（AC-006 対応）

```typescript
// Playwright から localStorage を直接読む
const save = await page.evaluate(() => localStorage.getItem('testquest:save'));
expect(JSON.parse(save!).status.knowledge).toBe(13);   // 10 + 3
```

- 画面側に数値が出ないことの検証：`screen-play` 配下のテキストに `/\d+\s*[%％]?/` がステータス領域に存在しないことを `status-bar-*` 要素内で確認する
- テキスト送り（30ms/文字）はE2Eの待ち時間を増やすため、`?skipTyping=1` のクエリパラメータで即時表示に切り替えるテスト用フックを設ける（本番UIに影響しない・E2E専用）

### 10.4 テストデータ用パス上書き（VITE_SCENARIOS_PATH・v1.1 追加）

異常系・境界のシナリオ検証（FR-009／テスト仕様書 §6 の `scenarios_test/`）で、本番データ（`public/data/scenarios/`）を汚さずに分離データを読ませるためのテスト用フックを設ける。クロスワードの `VITE_TERMS_CSV_PATH` 方式を踏襲する。

```typescript
// scenarioLoader.ts のベースパス解決
const SCENARIOS_BASE = import.meta.env.VITE_SCENARIOS_PATH ?? '/data/scenarios'
// loadIndex(): fetch(`${SCENARIOS_BASE}/index.json`)
// loadScenario(file): fetch(`${SCENARIOS_BASE}/${file}`)
```

- 環境変数未設定時は本番 `/data/scenarios` を指す（本番挙動に影響しない）
- テスト時は `VITE_SCENARIOS_PATH=/data/scenarios_test/<ケース> npm run dev` で分離データに切替。テスト後は環境変数なしで再起動すれば本番データへ自動復帰
- 要件7.4（保守性・コード変更なしでシナリオ追加）のテスト容易性を担保する。FR-009 のテスト手順は本フックを前提とする
