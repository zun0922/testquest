## 1. 背景と目的

### 1.1 現状の課題（PO指摘）

ステータス4種（知識・スキル・自信・チームワーク）は選択に応じて加算されるが、**ゲーム内で何にも使われていない**。UI-RULE-006 により数値も非表示のため、プレイヤーは成長を実感しにくい。

### 1.2 目的

**溜まったポイントをヒントという形で還元し、正解の積み重ねに意味を持たせる。**

ポイント量に応じてヒントが強くなる仕組みは **UI-RULE-006（数値非表示）と相性が良い**。数字を見せずに「育った実感」を返せるため、既存ルールを変えずに成立する。

## 2. 方式（PO決定 2026-08-30）

| 論点 | 決定 |
|------|------|
| ヒントの形式 | **ヒント文（主）＋選択肢の重要語の強調（補助）**。ヒント文が「**何を考えるか**」を、強調が「**どこを見るか**」を示す。他の案（シラバス項番の先出し／誤答の除外／解説の先出し）は不採用<br>※当初は強調のみだったが、STEP 2 のPO確認「強調表示だけでは微妙。テキストの方が親切」を受けてヒント文を追加した（v0.3） |
| ポイントとの対応 | **4種の合計**でヒントの強さが決まる（種類別の割り当ては行わない） |
| 発動方法 | **任意**。「ヒントを見る」ボタンを押したときだけ表示する |

### 2.1 なぜ「選択肢」を強調するのか（実データによる裏づけ）

当初案は「問題文の重要箇所」の強調だったが、実データを確認したところ**問題文は20〜30字の短い問いかけ**で、強調する余地がほとんどなかった。

```
q1: 「あなたの考えを聞かせて。テストとは何をすること？」
```

状況説明は直前の `intro` ノード群にあり、**判断の核心は選択肢の側**にある。

```
[good] 動的に実行して欠陥を探すこと          ← 「動的」だけを指す＝部分正答
[best] 欠陥を見つけ品質を評価する一連の活動
[poor] 仕様どおりにプログラムを作ること        ← これは開発であってテストではない
```

選択肢の重要語を強調すれば「**どこが論点か**」を示せる一方、**答えそのものは教えない**。学習教材として妥当なバランスになる。

### 2.2 機械生成できないことの確認

解説文（`feedback.explanation`）と問題文の共通語を抽出する方法を試したが、「テスト」「技法」のような一般語しか取れず、AL-TTA では共通語ゼロだった。**強調範囲はデータとして持つ必要がある。**

## 3. ヒントの段階（実測に基づく閾値）

### 3.1 ポイントの実測値

開始値は 40（各10×4）、最大 400（各100×4）。極端な2ケースだけでは閾値を決められないため、**中位のプレイも合わせて実測**した。

| プレイ | FL第1章終了 | **FL編終了（＝AL解放時点）** | AL-TM編終了 | 全71本終了 |
|--------|-----------|--------------------------|------------|-----------|
| 全問 best | 124 | **366** | 400 | 400（50本目で上限到達） |
| best/poor 交互 | 91 | **279** | 378 | 385 |
| 3問に1問 best | 79 | **232** | 339 | 366 |
| 全問 poor | 58 | **130** | 162 | 183 |

**AL編に入る時点のポイントは 130〜366 と幅が大きい**。この幅が、レベル別閾値を設計するうえでの前提になる。

### 3.2 ヒントの強さ（3段階）

| Lv | ヒントの内容 |
|----|------------|
| **Lv0** | **使用不可**（ボタン非活性）。自力で考える |
| **Lv1** | **ヒント文を表示**（何を考えればよいかを示す。選択肢の強調はしない） |
| **Lv2** | **ヒント文＋全選択肢の重要語を強調**（考える観点と、それが選択肢のどこにあるかが両方見える） |

強調で特定の選択肢だけを光らせると正解が割れてしまうため、Lv2 では対象を絞らず**全選択肢**を強調する。

### 3.3 閾値はレベル別（PO決定 2026-08-30）

**同じポイントでも、FL ではヒントが出やすく、AL では出にくい。** 上級ほど自力で考えることを求める設計。

| プレイ中のシナリオのレベル | Lv1 | Lv2 |
|------------------------|-----|-----|
| **FL** | **60** | **150** |
| **AL-TM / AL-TTA** | **170** | **300** |

判定は**プレイ中のシナリオの `level`** で切り替える（同じセーブデータでも、FL の問題では出て AL の問題では出ない、という状態が起こりうる）。

#### 実測値との突き合わせ

| プレイ | FL第1章終了時（FL判定） | FL編終了時（AL判定） | 全71本終了時（AL判定） |
|--------|----------------------|--------------------|---------------------|
| 全問 best | 124 → **Lv1** | 366 → **Lv2** | 400 → Lv2 |
| best/poor 交互 | 91 → **Lv1** | 279 → **Lv1** | 385 → **Lv2** |
| 3問に1問 best | 79 → **Lv1** | 232 → **Lv1** | 366 → **Lv2** |
| 全問 poor | 58 → **Lv0** | 130 → **Lv0** | 183 → **Lv1** |

設計上の狙い：
- **FL の序盤は Lv0**（自力で数本進める）。poor 続きでも第1章の終盤で Lv1 に届く
- **AL に入った時点で一度 Lv が下がる**（同じポイントでも AL の閾値が高いため）＝上級では自力で考えさせる
- **どのプレイでも最終的に何らかのヒントに到達する**（poor 一辺倒でも AL 終盤で Lv1）
- 正解を積むほど早く強いヒントに届く＝**正解の報酬**として機能する

> **注**：AL-TM と AL-TTA は同じ閾値とした（PO指示は「FL が低く AL が高く」）。AL-TTA をさらに高くする案もあるが、両者は FL 全クリアで**同時に解放**されプレイ順が自由なため、区別する必然性は薄いと判断した。

## 4. データ設計

### 4.1 スキーマ拡張（`Choice` に `emphasis` を追加）

```jsonc
{
  "text": "動的に実行して欠陥を探すこと",
  "rating": "good",
  "emphasis": ["動的に実行"],          // 追加（省略可）
  "statusEffects": { "knowledge": 2 },
  "feedback": { "explanation": "...", "syllabusRefs": ["1.1"] },
  "next": "q2"
}
```

- **`emphasis`：`string[]`（省略可）**。`text` 内の部分文字列を指定する
- **既存の `text` は一切変更しない**（監修済み本文を不変に保つため、本文へのマークアップ埋め込みは採らない）
- 実装は `text` 内の該当箇所を `<strong>` でラップして色を当てる

### 4.2 ヒント文（`ChoiceNode` に `hint` を追加）

```jsonc
{
  "id": "q1",
  "type": "choice",
  "text": "あなたの考えを聞かせて。テストとは何をすること？",
  "hint": "テストが指す範囲はどこまででしょうか。実行することだけを指していないか、確かめてみましょう。",  // 追加（省略可・最大100字）
  "choices": [ ... ]
}
```

#### 書き方のガイドライン（全章展開時の起案基準）

| 原則 | 内容 |
|------|------|
| **答えを言わない** | 「正解は〜」「〜が正しい」と書かない。**どれが正解かは示さず、考える観点だけ**を示す |
| **用語で名指ししない** | 正解の根拠となる専門用語をそのまま出すと答えになる（例：q3 で「妥当性確認」と書かない） |
| **問いの形にする** | 「〜でしょうか」「〜を考えてみましょう」と、思考を促す言い回しにする |
| **長さ** | 40〜60字を目安に、**最大100字**（`LIMITS.HINT_MAX`）。読む負担を増やさない |
| **1問1文〜2文** | 論点は1つに絞る |

起案例（`fl-1-01`）：

| 問題 | ヒント文 |
|------|---------|
| q1 テストとは何をすること？ | テストが指す範囲はどこまででしょうか。実行することだけを指していないか、確かめてみましょう。 |
| q2 何を達成したいか | テストの目的は一つだけでしょうか。欠陥を見つけること以外にも果たす役割があります。 |
| q3 要件どおりか確認すれば十分か | 確かめるべきことは一種類でしょうか。仕様に合っているかだけで足りるか考えてみましょう。 |
| q4 欠陥が見つかった。次は？ | テストとデバッグは別の活動です。テスターの担当がどこまでで、その後に何が続くかを考えてみましょう。 |

### 4.3 検証（validator・門番テスト）

| 検証 | 内容 |
|------|------|
| 包含 | `emphasis` の各要素が `text` に**実在すること**（含まれないと強調されず、データの空振りになる） |
| 重複 | 同一 `text` 内で強調範囲が重ならないこと |
| 件数 | 1選択肢あたり **1〜2語**（強調しすぎると論点がぼやける） |

| ヒント文 | `hint` は空でない文字列・**最大100字**（検証 **#14**） |

既存の検証12項目に **#13（emphasis）・#14（hint）** を追加し、`scenarios.data.test.ts` の門番で全数検証する。

### 4.4 データ整備の規模

| データ | 件数 | 内容 |
|--------|------|------|
| **ヒント文**（`hint`） | **280問** | 1問1文〜2文。**こちらが主役** |
| 強調範囲（`emphasis`） | 840選択肢 | 1選択肢あたり1〜2語。Lv2 でのみ使う補助 |

- どちらも**本文を作るのではなく既存の文から観点や語を選ぶ**作業なので、シナリオ制作より軽い
- AI がバッチで起案し、POが監修する（シナリオ制作と同じフロー）
- **`hint` だけ先に整備して `emphasis` を後回しにする**こともできる（どちらも省略可で、片方だけでもヒントは出る）

### 4.4 整備の順序（PO決定 2026-08-30）

**まず数問で試作し、POが実画面で効果を確認してから全章に適用する。**

| STEP | 内容 | 判断 |
|------|------|------|
| 1 | ✅ `fl-1-01` の4問で試作（2026-08-30） | — |
| 2 | ✅ **PO確認**「いい感じ」＋「テキストでヒントを出した方が親切」→ ヒント文を主役に構成変更 | PO |
| 3 | ✅ **全章展開完了**（2026-08-30）：**280問すべてに `hint`**／**840選択肢中837に `emphasis`** | AI |

**未付与3件について**：`al-tta-3-01/q2` の選択肢は「3」「2」のように**1〜2文字の数値回答**で、強調しても論点を示せないため意図的に省略した。
ヒント文は付いているので、この問題でもヒントは機能する（`hasHintData` がヒント文か強調のどちらかで判定するため）。

**挿入方法**：`scripts/apply-hints.mjs`（データJSONを渡すと行ベースで挿入）。`JSON.parse`→`stringify` で書き戻すと既存の整形が崩れて差分が膨らむため、**行ベースで該当行だけを挿入**する。
事前に「hint が100字以内」「emphasis の語が選択肢 text に実在する」を全件検証し、1件でも違反があれば何も書き換えずに終了する。

**実績**：71ファイル・**1,117行の追加・削除0**（本文は一切変更していない）

`emphasis` は**省略可**なので、STEP 1 の時点でも他の問題は従来どおり動く（データのない問題はボタン非活性）。音声と同じ段階導入の考え方。

## 5. UI

| 項目 | 仕様 |
|------|------|
| 配置 | 選択肢オーバーレイ内（`ChoiceOverlay`）に「ヒントを見る」ボタン |
| 非活性 | Lv0 のとき、およびその問題に `emphasis` データが無いとき |
| 表示 | 押下で選択肢内の該当語を強調（太字＋アクセント色）。**一度押したらその問題の間は表示したまま** |
| 状態 | 選択肢を選ぶと解除（次の問題では再度押す） |
| 数値 | **一切表示しない**（UI-RULE-006 を維持）。ボタンの活性/非活性でポイントの育ち具合が間接的に伝わる |

## 6. 受け入れ基準（案）

| AC | 基準 |
|----|------|
| AC-P2-007-1 | 合計ポイントが Lv0 の範囲のとき、ヒントボタンが非活性である |
| AC-P2-007-2 | Lv1 でボタンを押すと、**ヒント文が表示される**（選択肢の強調はされない） |
| AC-P2-007-3 | Lv2 でボタンを押すと、**ヒント文に加えて全選択肢**の重要語が強調される |
| AC-P2-007-4 | ヒント文・強調データのどちらも無い問題ではボタンが非活性である |
| AC-P2-007-5 | ヒント表示中も**数値・%が画面に出ない**（UI-RULE-006） |
| AC-P2-007-6 | `emphasis` の各要素が `text` に実在すること・`hint` が100字以内であることを門番テストが検証する |
| AC-P2-007-7 | 問題が変わるとヒント表示がリセットされる（前の問題の表示を持ち越さない） |

## 7. 学習効果への配慮

- **ヒント文は答えを言わない**（§4.2 のガイドライン）。観点だけを示し、判断は学習者に残す
- 強調するのは**論点であって答えではない**。特定の選択肢だけを光らせて正解が割れる形は採らない（Lv2 は全選択肢を強調する）
- 任意表示（ボタン）としたのは、**自分で考えてから見られる**ようにするため

## 8. PO判断の記録（2026-08-30）

| # | 論点 | 決定 |
|---|------|------|
| ① | 閾値 | **FL は Lv1=60 を採用**。加えて**レベル別に設定**する（FL は低く・AL は高く）＝§3.3 |
| ②③ | 監修範囲と整備順序 | **数問で試してから全章適用**。監修方法は試行の結果を見て決める＝§4.4 |
| ④ | 上限到達 | **レベル別閾値にしたことで発生しづらい**とのPO判断。AL の Lv2 を 300 に置いたため、400 到達前に最大のヒントに届く |

> ④について補足：**「400到達後の正解がステータス上は無意味」という事実自体は変わらない**（ヒント機能の観点では実害が小さい、という判断）。将来ステータスに別の用途を与える場合は再検討が必要。

## 9. 残る確認事項

| # | 内容 |
|---|------|
| A | **poor 一辺倒のプレイでは AL 編の大半でヒントが使えない**（FL編終了時130 → AL の Lv1=170 に未達）。AL 終盤でようやく Lv1 に届く。上級者向けの厳しさとして意図どおりか、AL の Lv1 をさらに下げるか |
| B | ヒントを使ったことを**結果画面に表示するか**（「ヒント使用 2回」等）。学習の振り返りには有用だが、UI-RULE-006 の抽象表現方針との兼ね合いがある |
