## 1. 基本方針

v10.1 から継承する4原則：

- **AIが作る、人間が判断する。** 実装・ドキュメント生成・テスト実行はAIが担い、内容の正しさの確認・承認・最終判断は人間（PO）が行う
- **工程ごとにインプットとアウトプットを明確にする。**
- **人間のレビューなしに次工程へ進まない。** AIが完成と判断しても承認なしに次工程へは進まない
- **曖昧な指示は作業開始前に解消する。** 推測で進めない

TestQuest で追加された3原則（実績から確立）：

- **決定的処理＞生成的処理**（2026-07-03 PO評価済み）。既存の成果物に手を入れるときは、まず結果が一意に決まる処理（クロップ・スクリプトによる部分編集）で試みる。生成的処理（AI再生成・re-roll）は同一性が壊れるため最後の手段
- **既存分の不変を優先する。** データ改訂は「追加のみ・既存行は変更しない」を原則とし、差分で機械的に証明する（例：かく乱肢改訂5バッチとも `git diff` で追加のみ・削除0を確認）
- **成功表示を疑い実体を検証する。** ツールの成功報告や記憶ではなく、ファイル・本番配信・差分を実際に読んで確認してから完了を報告する（2026-07-11 の不実報告インシデントの教訓）

## 2. 役割定義

### 人間（PO・y.koizumi）

| 責務 | 具体的な作業 |
|------|-------------|
| 要件の決定 | 何を作るかを決める。企画書・要件定義書・設計書のレビューと承認 |
| **学習コンテンツの監修承認（AC-012）** | シナリオ起案の内容妥当性（シラバス適合・評価基準・かく乱肢）を確認し承認する。**TestQuestで最も重要な品質ゲート** |
| **画像アセットの採用判断** | 生成された候補から採用案を決定する（STEP B/D） |
| 通しプレイ総合確認 | 読み味・演出・学習体験など人間の目でしか確認できない品質の確認（`docs/通しプレイ確認シート_v0.1.md`） |
| 問題発生時の判断 | 仕様変更・優先順位変更・リスク対応方針の決定 |
| デプロイ・push 判断 | 本番リリース（`git push` によるVercel自動デプロイ）のGOサイン |
| 費用の承認 | 課金API（画像生成）の実行可否 |

### AI（Claude Code）

| 責務 | 具体的な作業 |
|------|-------------|
| 実装 | 設計書に基づくコンポーネント・ロジックの実装 |
| 自動テスト | 単体テスト・E2E の作成・実行・レポート |
| ドキュメント生成 | 要件定義書・設計書・テスト計画書/仕様書/手順書・起案書の作成 |
| **シナリオ起案・JSON化** | シラバス精読→起案→（監修承認後）JSON化→検証 |
| **画像アセット生成・組み込み** | 設定書に基づく生成・透過・圧縮・配置 |
| セルフレビュー | 出力前に self-review.skill の汎用5観点で自己点検 |
| 権利確認 | 規約・類似性逆引き・プロンプト監査・写り込み確認（手順は image-asset-production.skill `references/rights-check.md`） |
| 記録 | worklog・宿題リスト・採用記録・CLAUDE.md TODO の更新 |
| 不明点の確認 | 着手前に曖昧な点を確認する |

> **AIにできないこと：** 要件の決定、**学習コンテンツの内容妥当性の最終保証**（シラバス解釈は監修が正）、画像の採用判断、本番デプロイ判断、コスト・契約関連の判断

## 3. 開発フローの全体像

TestQuest には性質の異なる4系統のフローがある。**どの系統でも「AIが作り、人間が承認してから次へ進む」構造は共通**。

```
① 実装フロー（§4）        ：機能・UI の追加改修
   STEP 1 仕様確認 → 2 設計 → 3 設計レビュー → 4 実装 → 5 セルフレビュー → 6 検証

② シナリオ制作フロー（§5） ：学習コンテンツ＝プロダクトの中核
   STEP 1 範囲確定 → 2 起案 → 3 監修承認(AC-012) → 4 JSON化 → 5 セルフレビュー → 6 検証

③ 画像アセット制作フロー（§6）：立ち絵・背景
   STEP 0 設定定義 → A 基準画像 → B 採用判断 → C 表情差分 → D 一貫性確認
                                → E 権利確認 → F 組み込み

④ スキル・ルール改訂フロー（§7）：AIの作業品質そのものの改善
   STEP 1 精査 → 2 改訂起案 → 3 PO承認 → 4 適用 → 5 再パッケージ検証 → 6 連動更新
```

### リリースまでの流れ（全系統共通）

```
各系統の STEP 6（検証）完了
       ↓
PO 確認（実画面スクショ・監修・通しプレイ）
       ↓
commit → push（**PO指示時のみ**）→ Vercel 自動デプロイ＋CI
       ↓
本番スモーク（AI・§8.4）
       ↓
完了報告
```

## 4. 実装フロー（STEP 1〜6）

### STEP 1　仕様確認

| | 内容 |
|--|------|
| 担当 | AI（質問）→ PO（回答） |
| インプット | 企画書・要件定義書・設計書・前工程の成果物 |
| アウトプット | 質疑応答ログ（チャット上で完結） |
| 完了条件 | AIが着手可能と判断し、POが作業開始を許可した |
| 注意 | 曖昧な点を全て確認してから着手する。**選択肢を出すときは推奨を先頭に置き、実測データを添える** |

### STEP 2　設計

| | 内容 |
|--|------|
| 担当 | AI |
| アウトプット | 設計書（Markdown）。コンポーネント構成・型定義・処理フロー・ファイル構成・視覚設計・画面レイアウト・data-testid 一覧 |
| 完了条件 | 設計書が出力されレビュー待ちになった |
| 注意 | 設計書承認前にコードを書かない |

- **モックが先行して存在する場合**：モックを「レイアウト・デザインの正」と設計書に明記し、差分のみテキスト定義する（TestQuest では `docs/mockup_a案_ビジュアルノベル風.html` が承認済みレイアウトの正）
- **レイアウト詳細の先行策定（必須）**：サイズ計算・最低幅高さ・折り返し方針・モバイル差異を実装前に確定する。実装後のレイアウト問題は仕様変更・修正・テスト再実施が連鎖する
- **カラーはトークン化する**：確定色は `tailwind.config.ts` にトークンとして定義しハードコードを避ける（例：`cleared: '#8ef0c4'`）

### STEP 3　設計レビュー

| | 内容 |
|--|------|
| 担当 | PO |
| 完了条件 | POが「承認」を明示的に伝えた |

**レビュー観点**：要件定義書との整合性／技術的実現可能性／将来拡張への影響／ライセンス／モックとの整合

### STEP 4　実装

| | 内容 |
|--|------|
| 担当 | AI |
| アウトプット | ソースコード・単体テスト・E2E・テストレポート |
| 完了条件 | 型チェック通過・単体テスト全件PASS・E2E全件PASS |
| 注意 | 仕様にない機能を勝手に追加しない。スコープ外の改善は提案として報告する |

- **テスト容易性フックを使う**：`?skipTyping`（タイプライター演出の省略）・`VITE_SCENARIOS_PATH`（異常系データ切替）・`?unlockAll=1`（dev限定・本番バンドルから除去されることを確認する）
- **E2E は可変要素に依存しない書き方にする**：ノード数・本数の増減で壊れないセレクタ・進行方法を使う（例：選択肢が出るまで送る `advanceToChoice`）。スクリーンショットは**画像デコード完了待ち**（`waitForImages`）を入れる

### STEP 5　AIセルフレビュー

| | 内容 |
|--|------|
| 担当 | AI |
| 完了条件 | 全観点でレビューし重大な指摘をゼロにしてから出力する |

**汎用5観点**（self-review.skill・全成果物に適用）：①上流との整合性 ②文書内の一貫性 ③網羅性 ④明確性 ⑤次工程への移行可否

**コード固有の観点**：仕様準拠／エラーハンドリング（**シナリオJSONのロード失敗・不正データ・localStorage 利用不可**）／セキュリティ／パフォーマンス／型安全性（型エラー0件）／**ライセンス（`LICENSES.md` に記載したか）**

**仕様変更時の文書連鎖確認ルール（必須）**

仕様変更を含む場合、2層で影響を確認する。

- **層1（本流）**：要件定義書 → 設計書 → テスト計画書 → テスト仕様書 → テスト手順書
- **層2（派生・補助）**：企画書／宿題リスト／画像デザイン設定書・プロンプト集・採用記録／シナリオ起案書群／通しプレイ確認シート／CLAUDE.md／`.claude/rules/project/`／スキル

手順：層1を上流→下流に走査 → CLAUDE.md §3 と §6 から層2の一覧を取得し全件で影響有無を判定 → **影響なしと判定した文書も worklog に「影響なし確認済み」と記録**する。

### STEP 6　検証

TestQuest の検証は §8「検証体制」に従う。**人間による機能テスト（ブラウザ操作）は自動E2E＋実画面スクショ確認で代替している**のが実態であり、テストログCSVの記入運用は稼働していない（§9）。

## 5. シナリオ制作フロー

学習コンテンツはこのプロダクトの中核であり、**監修承認（AC-012）が最重要の品質ゲート**である。詳細な判断基準は `skills/scenario-authoring.skill`（評価基準・配分ルール・かく乱肢設計・validator 12項目・落とし穴）が正。

| STEP | 担当 | 内容 |
|------|------|------|
| 1 範囲確定 | AI→PO | 対象章・シラバス範囲・本数・分割単位を決める。**ALは分割起案が原則**（1起案に過大な肢数を詰めない） |
| 2 起案 | AI | シラバス抽出テキストを精読し、`docs/シナリオ起案_<範囲>_v0.1.md` を作成。**監修確認点を明示する**（①〜⑤形式） |
| 3 監修承認（AC-012） | PO | 内容妥当性を確認し承認 or 差し戻し |
| 4 JSON化 | AI | **決定的スクリプトによる部分編集**で適用。既存ノード・best・statusEffects・項番は不変 |
| 5 セルフレビュー | AI | 汎用5観点＋シナリオ固有（配分ルール・字数上限・「迷ったらpoor」） |
| 6 検証 | AI | データ品質門番（validator 12項目・章別本数・レベル別総数）＋単体＋E2E＋実画面スクショ |

**制作上の鉄則**

- **シラバスに根拠のない選択肢を作らない。** 起案時に抽出テキスト本文で照合し、根拠が見つからない案は自己差し替えする（実績：AL-TM第1章で1件、AL-TTAで1件を差し替え）
- **既存ノードは完全不変。** 改訂は追加のみで行い、`git diff` の削除行がゼロ（または `startNodeId` 等の意図した最小行のみ）であることを確認して報告する
- **人物像の取り違えに注意。** キャラクターの立場・口調は `docs/画像デザイン設定書_v0.1.md` §4 が正（ケン＝同期エンジニア。技術メンターではない。2026-07-03 の混同事故）
- **著作権配慮**：シラバス本文の逐語引用を避け、項番参照（`syllabusRef`）で紐づける

## 6. 画像アセット制作フロー

詳細は `skills/image-asset-production.skill` とルール `.claude/rules/project/image-assets.md` が正。

```
STEP 0　設定定義（AI→PO承認）：新規キャラ/背景は設定書に追記し承認を得てから生成
STEP A　基準画像生成（AI）　　：normal を複数案（デザイン探索は無料サービス可）
STEP B　採用判断（PO）　　　　：1案採用。不採用理由も採用記録に残す
STEP C　表情差分生成（AI）　　：採用画像を入力に Gemini 編集方式【編集方式必須】
STEP D　一貫性確認（PO）　　　：5表情を並べ「同一人物か・目は対称か」
STEP E　権利確認（AI実行＋PO確認）：規約・逆引き・プロンプト監査・写り込み
STEP F　組み込み（AI）　　　　：透過 → WebP圧縮 → 配置 → 単体+E2E → 実画面スクショ提示
```

**鉄則**

- 表情差分は**必ず編集方式**（テキストからの再生成は目のスケール・対称性が破綻する）
- **設定書にないキャラ・背景を生成しない**（設定書改版→PO承認が先）
- **課金APIは段階実行**（1枚テスト→確認→バッチ）とし、事前に費用概算をPOへ伝える
- **PO提示前に頭部比率を確認**（頭頂〜顎÷画像高≈47%）。ズレは再生成せずクロップで直す
- 配信形式は **WebP**（quality 90・`alphaQuality:100` 固定）。圧縮前PNG原本は `assets-candidates/original-png/` へ退避
- `public/images/` には**採用済みのみ**置く。候補は `assets-candidates/`

## 7. スキル・ルール改訂フロー

AIの作業品質そのものを改善する工程。改訂の起案基準は `skills/improvement-proposal.skill` が正。

| STEP | 担当 | 内容 |
|------|------|------|
| 1 精査 | AI | 現行版の全文を読み、改訂対象箇所を特定する |
| 2 改訂起案 | AI | 変更点と**PO決定点**を明示した起案を提示（大規模改訂は `docs/` に起案書を作成） |
| 3 承認 | PO | 承認 or 差し戻し |
| 4 適用 | AI | SKILL.md／references を改訂 |
| 5 再パッケージ検証 | AI | **.bak取得 → 再パッケージ → 再展開して全ファイル差分一致を確認**＋要点の存在を機械チェック |
| 6 連動更新 | AI | CLAUDE.md §1・関連ルール・worklog |

**`.skill` ファイル取り扱いの注意（2026-08-21 実測）**

- `.skill` はZIP。**多くは PowerShell `Compress-Archive` 製でパス区切りがバックスラッシュのため `unzip` が失敗する**（`unzip -p` が通るのは15件中3件のみ）。確実な読み方は `.zip` にコピーして `Expand-Archive -Force`、または `[IO.Compression.ZipFile]::OpenRead()`
- **`Compress-Archive` は `.skill` 拡張子を拒否する** → `.zip` に作って `.skill` へリネームする
- **PS5.1 の `Get-Content -Raw` は既定ANSI解釈**。日本語を含む機械チェックには `-Encoding UTF8` を付ける（付けないと検証が空振りする）

## 8. 検証体制（実態）

TestQuest で実際に稼働している検証はこの6層である。**上位層が下位層の代替にはならない**。

| 層 | 種別 | 担当 | 内容 |
|---|------|------|------|
| 1 | 型チェック | AI（自動） | `npm run typecheck`（型エラー0件） |
| 2 | 単体テスト | AI（自動） | `npm test`＝**153件**。utils各種＋**データ品質門番**（後述） |
| 3 | E2E | AI（自動） | `npm run test:e2e`＝**15件**（walkthrough／persistence／select-collapse／orientation）。受け入れ基準 AC-001〜010 を網羅 |
| 4 | 実画面確認 | AI提示→PO | `e2e-shots/` のスクリーンショットで演出・立ち絵・レイアウトを確認 |
| 5 | 監修承認（AC-012） | PO | 学習コンテンツの内容妥当性。**全71本を全数承認**（サンプリングではない） |
| 6 | 通しプレイ総合確認 | PO | 読み味・テンポ・表情整合・評価の納得感（`docs/通しプレイ確認シート_v0.1.md`・観点C1-C6/A1-A5/X1-X5） |

### 8.1 データ品質門番（層2の中核）

シナリオJSONは**コードと同じ厳しさでテストする**。`src/utils/scenarios.data.test.ts` が全71本に対して実行する。

- `validator.ts` の**12項目**（必須フィールド・ID一意性・遷移先の存在・到達可能性・字数上限〔本文200字・選択肢40字・解説400字〕・rating の妥当性・項番形式 等）
- **章別の本数・レベル別総数・全体71本**の一致（データ追加漏れ・取りこぼしの検出）
- 項番規約（FL＝`x.y`／AL-TM＝`TM-x.y.z`）

### 8.2 CI

`.github/workflows/ci.yml`：push/PR で 型 → 実行時依存の脆弱性 → 単体 → E2E を実行。

### 8.3 ローカル検証の順序（AIの標準手順）

```
npm run typecheck → npm test → npm run build → npm run test:e2e
```

ビルドを E2E より前に置く（本番バンドルの問題を先に検出する）。

### 8.4 本番スモーク（push後・必須）

デプロイ後、**実配信を機械的に確認**してから完了を報告する。過去の実施例：

- データ変更時：**本番URLから全71本を取得して全数検証**（設問数・選択肢数・改訂内容の反映）
- 画像形式変更時：**全27枚の HTTP 200 と `Content-Type`**、旧形式が404であること、本番バンドル内の EXT リテラル
- 共通：トップ HTTP 200・`index.json` の本数・dev限定フラグが本番バンドルに含まれないこと

## 9. 不具合対応

### 9.1 実態（軽量ループ）

現在の規模では、検出から修正までを軽量ループで回している。

```
検出（自動テストのFAIL／PO指摘／本番スモークの不一致）
    ↓
原因分析（AI）※同じ修正を3回繰り返したら根本原因の見直しへ
    ↓
修正 → セルフレビュー → 該当層の再検証（層2〜4）
    ↓
PO報告（症状・原因・対応・再発防止）
    ↓
worklog に記録
```

- **修正は必ず該当層より下位の層から再実行する**（データ修正なら層2の門番から）
- **回帰確認を省略しない**：既存の単体・E2E が無改変で通ることを確認して報告する

### 9.2 未稼働の枠（必要時に起動する）

以下は v10.1 から枠として引き継ぐが、**現在は運用していない**。人間による機能テストを本格実施する段階（宿題B-3のTD群準備後）で起動する。

- **テストログCSV運用**：AIが `test_id`・`test_case`・`expected` を生成し、人間が `actual`・`result`・`notes` を記入する方式。形式は**テスト仕様書§7「テストログCSV雛形」**が正
- **不具合管理リスト（DEF-XXX）**：重大度（Critical/High/Medium/Low）× 優先度（P1〜P4）の2軸管理。`status`：Open / Fixed / Verified / Closed / Reopened
- 起動条件：①人間による機能テストを実施する ②不具合が単一セッションで完結せず持ち越す ③複数人が関与する

> 未稼働のものを「運用中」と書かないのは、実態と乖離した文書が判断を誤らせるため（本書 v0.1 の方針・PO決定 2026-08-21）。

## 10. 中断・再開の仕組み

Claude Code のセッションは記憶を持たないため、明示的な引き継ぎが必須。

### 中断時にAIが行うこと

1. **CLAUDE.md §6 TODO の最新化**（完了✅／進行中🔄＋現在の状態／新規🔲）
2. **`docs/worklog.md` に追記**（形式は下記）
3. **次のアクションを明示**
4. **未コミットの差分を整理**（commit/push は PO 指示時。§14.3）

### worklog の形式（TestQuest の実運用形式）

```markdown
## YYYY-MM-DD（追記N）
**着手内容：** [作業内容と、それを始めた経緯（PO指示の引用）]
**完了内容：**
- **STEP n（工程名）：** [実施内容。判断の根拠と数値を含める]
**検証（STEP 6）：** [型・単体件数・E2E件数・実画面確認]
**残る注意点：** [未解決事項・後続への申し送り]
**次のアクション：** [次に着手すべき作業]
```

- **追記番号は連番**で、既存の追記は書き換えず末尾に追加する
- **本番反映は「完了内容（追記・本番反映）」として同じ追記に追補**する（コミットハッシュ・スモーク結果を含む）
- 数値・ファイルパス・コミットハッシュを具体的に書く。「うまくいった」ではなく「単体153件 全PASS」と書く

### 再開時にAIが行うこと

1. CLAUDE.md を読み込む（セッション開始時に自動ロードされる）
2. worklog の末尾（直近の追記）を確認する
3. **TODO の記載を実体と突き合わせる**（記載が古い場合がある。2026-08-21 に「AL実装の残作業」3件が実は完了済みと判明した実例）
4. 状況をPOに報告してから着手する

### セッション切替時のチェックリスト

中断時：□ TODO 更新 □ worklog 追記 □ 未コミット差分の整理 □ PO確認事項の明示
再開時：□ CLAUDE.md 読込 □ worklog 末尾確認 □ **TODO と実体の突き合わせ** □ 状況報告

## 11. コミュニケーション基準

### 11.1 報告のタイミング

| タイミング | 報告内容 |
|----------|---------|
| STEP完了時 | 完了STEP・成果物・次STEPの予告 |
| セルフレビュー後 | 結果（重大指摘の有無・修正内容） |
| 判断要請時 | 状況＋**選択肢＋推奨**（y-koizumi-profile.skill §6） |
| 起案完了時 | 「監修レビューをお願いします」と明示し、**監修確認点を列挙**する |
| 課金API実行前 | **費用概算**（枚数×単価）を提示する |
| push前 | 変更内容とスモーク計画を示し、**PO指示を待つ** |
| 本番反映後 | スモーク結果（機械的に確認した数値） |
| 問題発見時 | 仕様の矛盾・実現困難な要件は即座に報告 |
| スコープ外の改善 | 提案として報告するが勝手に実装しない |

### 11.2 エスカレーション（作業を止めて即報告）

- セキュリティリスク・情報漏洩リスクを発見した場合
- **本番データ・採用アセットの破損や汚染が疑われる場合**
- 上流ドキュメントの矛盾を発見した場合
- **同じ修正を3回以上繰り返している場合**
- 仕様変更が必要と判断した場合
- **ライセンスがポリシーに抵触する依存を追加せざるを得ない場合**（`.claude/rules/common/workflow/licensing-policy.md`＝GPL系は原則不採用）

### 11.3 報告の長さ

要点を先に、短く。STEP完了3行以内／セルフレビュー結果5行以内／判断要請は状況1〜2行＋選択肢＋推奨。**数値と根拠は省略しない**（長さの節約より正確さを優先する）。

### 11.4 用語の統一

| 使う用語 | 使わない用語 |
|---------|------------|
| 機能テスト | 受け入れテスト・UAT |
| 差し戻し | リジェクト・NG |
| 承認 | OK・LGTM |
| 実装 | コーディング・開発 |
| 監修（承認） | レビュー（内容妥当性の確認は「監修」で統一） |
| 決定ポイント | 問題・クイズ |
| かく乱肢（distractor） | ダミー選択肢 |
| 立ち絵 | キャラ画像・スプライト |
| PO | 依頼者・ユーザー（人間側の意思決定者を指すときは PO） |

## 12. 完了判定とリリース判断

### 完了の階層

```
プロジェクト完了 ← フェーズ完了（Phase 1/2/3） ← マイルストーン完了 ← タスク完了
```

### タスク完了の定義

| 種別 | 完了条件 |
|------|---------|
| 実装 | 実装完了・セルフレビュー・型チェック通過・単体+E2E PASS |
| ドキュメント | 記述完了・セルフレビュー・**PO承認** |
| **シナリオ** | 監修承認（AC-012）・JSON化・**データ品質門番クリア**・実画面確認 |
| **画像アセット** | PO採用（STEP B/D）・権利確認（STEP E）・組み込み・回帰PASS |
| 不具合修正 | 修正・セルフレビュー・該当層の再検証PASS・回帰PASS |

### リリース（push）の必須条件

| # | 条件 | 確認方法 |
|---|------|--------|
| 1 | 型チェック通過 | `npm run typecheck` |
| 2 | 単体テスト全件PASS | `npm test`（データ品質門番を含む） |
| 3 | E2E全件PASS | `npm run test:e2e` |
| 4 | 本番ビルド成功 | `npm run build` |
| 5 | コンテンツ変更なら**監修承認済み** | 起案書のPO承認記録 |
| 6 | 画像変更なら**PO採用＋権利確認済み** | 採用記録 |
| 7 | 依存追加なら **LICENSES.md 更新済み** | 差分 |
| 8 | ドキュメント連鎖の確認済み | worklog に記録 |
| 9 | **POのpush指示** | チャット上の明示的指示 |

**push後は本番スモーク（§8.4）が完了するまでタスク完了としない。**

### 条件付きリリースの判断（v10.1 のフレームワークを継承）

未達成項目を3軸（影響範囲・発生頻度・検知容易性／各1〜3点）でスコアリングし、積で判定する。

| スコア | 判定 |
|--------|------|
| 1〜6 | AIの判断でリリース可（事後報告） |
| 7〜12 | PO判断が必要 |
| 13〜27 | リリース不可（修正後に再判定） |

**セキュリティ・データ完全性・権利関連は本フレームワークの対象外**とし、未達成なら無条件でリリース不可。ただし**POがリスクを了承して公開する判断はPOの権限**（実績：B-4未了での社内パイロット公開＝2026-07-04 PO了承）。

## 13. データ品質保証

TestQuest の「データ」は**シナリオJSON（学習コンテンツ）**が中心であり、これはプロダクトの価値そのものである。

### データ種別と品質責任

| 種別 | 例 | 一次作成 | 品質責任者 |
|------|-----|---------|----------|
| **学習コンテンツ** | `public/data/scenarios/**.json`（71本） | AI（シラバス参照で起案） | **PO（監修承認・全数）** |
| 索引 | `index.json` | AI | AI（門番テストで機械保証） |
| 画像アセット | `public/images/**.webp`（27枚） | AI（生成） | PO（採用判断） |
| テストデータ | `scenarios_test/`（TD-XXX） | AI | AI＋PO承認 |
| 設定 | 環境変数・`.env.local` | 人間（環境固有） | 人間 |

### 品質の評価軸（DAMA-DMBOK の6軸）

完全性／正確性／一貫性／適時性／一意性／妥当性。シナリオJSONでの具体化：

| 軸 | シナリオJSONでの意味 | 検証方法 |
|----|-------------------|---------|
| 完全性 | 必須フィールド・章別本数が揃っているか | 門番テスト（章別本数・総数71本） |
| **正確性** | **シラバス記述と一致し、評価（best/good/poor）が妥当か** | **監修承認（AC-012）＝人間** |
| 一貫性 | 項番形式・キャラ口調・トーンが揃っているか | 門番（項番規約）＋起案時の照合 |
| 一意性 | ID重複がないか | validator（ID一意性） |
| 妥当性 | 字数上限・rating・遷移先が規約内か | validator 12項目 |
| 適時性 | シラバス版との対応が維持されているか | `syllabusRef` の項番参照 |

### 3層チェック

```
Layer 3：監修承認（PO・全数）        ← 内容の正しさ
Layer 2：validator + 門番テスト（コード） ← 構造・規約の正しさ
Layer 1：起案時のシラバス照合（AI）    ← 根拠の有無
```

- **Layer 1**：起案時に抽出テキスト本文で根拠を確認し、**根拠のない案は自己差し替えする**
- **Layer 2**：`src/utils/validator.ts`（12項目）＋ `scenarios.data.test.ts`（本数・項番規約）。**CIで毎push実行される**
- **Layer 3**：**サンプリングではなく全数監修**（クロスワードの用語CSVは10〜20%サンプリングだったが、TestQuestは1本ずつ起案→承認するため全数が成立する）

### 14.3 判断・承認ルール

**POの承認が必要（AIは勝手に進めない）**

| シチュエーション | 理由 |
|----------------|------|
| 設計書 → 実装への移行 | スコープ・技術選定の確認 |
| **シナリオ起案 → JSON化**（監修承認） | 学習内容の妥当性はAIが保証できない |
| **画像の採用・設定書にないキャラ/背景の生成** | デザイン判断・世界観の一貫性 |
| **課金APIの実行** | 費用が発生する |
| **`git commit` / `git push`（本番デプロイ）** | 不可逆・本番に即反映される（**運用方針：AIから頻繁にpushしない**） |
| 要件・仕様の変更 | 他成果物への連鎖 |
| **新しい依存の追加** | ライセンスリスク（GPL系は原則不採用） |
| **スキル・共通ルールの改訂** | AIの作業品質全体に影響する |
| スコープ外機能の追加 | 工数・品質への影響 |

**AIが自己判断できるもの**

| シチュエーション | 条件 |
|----------------|------|
| 単体テスト・E2E失敗の修正 | 仕様変更を伴わない場合 |
| セルフレビュー指摘の修正 | 仕様変更を伴わない場合 |
| リファクタリング | 外部仕様・APIに変更なし。実施後に報告 |
| 誤字修正・記録の更新 | 内容・意味の変更を伴わない場合 |
| **一時ファイルの作成・検証スクリプトの実行** | scratchpad 内で完結し、リポジトリを汚さない場合 |
| **決定的処理による修正**（クロップ・部分編集） | 既存分が不変であることを差分で示せる場合 |

**差し戻し時のルール**：POは「何が問題か」と「期待する状態」を明示する。AIは修正方針を伝えてから着手し、修正後は同じ工程から再開する。
