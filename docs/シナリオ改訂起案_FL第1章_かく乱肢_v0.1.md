## 【設計指針】

### 制約
- **validator：1設問の選択肢は2〜3個**（4択は不可）。→ 改善は「**2択を廃止し原則3択**」＋「**poorを『明らかな誤り』から『惜しい誤答（distractor）』へ**」で行う。
- best選択肢テキスト ≤40字・解説 ≤400字・poorトーンガイドライン（受容→なぜ違うか→正しくは）は維持。

### かく乱肢（distractor）の3類型
| 型 | 内容 | 例（「○○と✕✕が正答」の場合） |
|----|------|------|
| **部分正答型** | 正しいが不完全（一部だけ／限定条件でのみ正） | 「○○である」だけ |
| **過剰型** | 正しいものに誤りを足す | 「○○と✕✕と△△である」 |
| **混同型** | 隣接概念との取り違え（もっともらしい） | 「デバッグ」を「テスト」と取り違え等 |

### 難易度傾斜（レベル別・本パイロットで確定 → 全章適用）
| レベル | 構成方針 | ねらい |
|--------|---------|--------|
| **FL（入門）** | 原則3択＝best＋惜しい誤答1＋明確な誤り1。**「明確な誤り」を1つ残し**、消去法の足がかりを確保 | 学び始めの安心感を保ちつつ、二択作業を脱する |
| **AL（TM/TTA・応用）** | 原則3択＝best＋**惜しい誤答2**（明確な捨て肢を置かない）。K4/K3は部分正答・過剰型を主軸 | 熟練者に歯応え。浅い分析ではpoorを選ぶ設計 |

### 評価（rating）の付け方
- **部分正答型で「限定的に正しい」もの** → `good`（副次解として加点・解説で不足を示す）。goodを意図的に増やす（現状1.6%が過少）。
- **過剰型・混同型・「十分」と言い切る誤解** → `poor`（+1加算・惜しいトーンで「なぜ惜しいか」を明示）。

## 【改訂案：全20問 before → after】

> 記法：各設問を `best` / `good` / `poor` で示す。★=今回追加/変更したかく乱肢。FL入門のため各問「明確な誤り」を1つ残す。

### fl-1-01 配属初日 〜テストって何？〜

**q1 テストとは何をすること？**
- before：best「欠陥を見つけ品質を評価する一連の活動」＋poor×2（実行して結果を見る／バグを修正する）
- after：
  - best「欠陥を見つけ品質を評価する一連の活動」
  - ★good「動的に実行して欠陥を探すこと」（部分正答＝動的テストのみ。静的テストと品質評価が抜ける）
  - poor「仕様どおりにプログラムを作ること」（混同＝開発と取り違え）

**q2 このテストで何を達成したい？**
- after：
  - best「欠陥検出・品質評価など目的を意識する」
  - ★good「できるだけ多くの欠陥を見つけること」（部分正答＝検出は目的の一つだが、品質評価・自信の提供・欠陥予防が抜ける）
  - poor「目的は考えず、とにかく動かす」（明確な誤り）

**q3 要件どおり確認すれば十分？（検証と妥当性確認）**
- after：
  - best「検証に加え、利用者ニーズ充足も確認する」
  - ★poor「要件を1つ残らず検証すれば十分」（惜しい＝検証はできているが妥当性確認〔ニーズ充足〕が抜ける・"十分"が誤り）
  - poor「動いていれば要件確認も不要だ」（明確な誤り）

**q4 欠陥が見つかった。次にやることは？**
- after：
  - best「故障を再現し原因を特定して直す（デバッグ）」
  - ★poor「欠陥レポートを書けばテスターの仕事は完了」（惜しい＝報告は正しいが"完了"は誤り。修正確認まで関与）
  - poor「テストの中でその場で直してしまう」（混同＝テストとデバッグの取り違え）

### fl-1-02 はじめてのテスト依頼 〜なぜテストするの？〜

**q1 テストの意義をどう説明する？**
- after：
  - best「欠陥を効率よく見つけ品質評価と判断材料を出す」
  - ★good「リリース前に欠陥を見つけて直せること」（部分正答＝検出は主要だが、品質評価・意思決定材料の提供が抜ける）
  - poor「バグをゼロにするため」（明確な誤り＝原則②に反する）

**q2 テストと品質保証（QA）は同じ？**
- after：
  - best「テストはQCの一種、QAはプロセスの予防活動」
  - ★poor「テストは品質を作り込む活動だ」（惜しい＝品質は開発で作り込む。テストは評価・検出）
  - poor「テストはQAそのものだ」（混同）

**q3 「エラー」「欠陥」「故障」の関係は？**
- after：
  - best「人のエラー→欠陥→(実行されると)故障」
  - ★poor「欠陥があれば必ず故障が起きる」（惜しい＝欠陥は実行され条件が揃って初めて故障。必ずではない）
  - poor「故障の原因は必ず人のミスだ」（過剰＝環境条件等も原因になりうる）

### fl-1-03 7つの道しるべ 〜テストの原則〜

**q1 「全部テストすれば安心」？**
- after：
  - best「全数テストは非現実的。技法と優先順位で集中」
  - ★poor「入力を全組み合わせ試せば全数達成できる」（惜しい＝組合せ爆発で現実には不可能）
  - poor「時間をかければ全部テストできる」（明確な誤り）

**q2 「バグが出ないから品質は完璧」？**
- after：
  - best「欠陥がないことは証明できない。妥当性確認も要る」
  - ★poor「テストを全部パスすれば欠陥ゼロと言える」（惜しい＝欠陥の不在は証明不可能・原則①）
  - poor「バグが出ないなら安心だ」（明確な誤り）

**q3 「同じテストを毎回繰り返す」？**（現状good有・維持し拡充）
- after：
  - best「同じテストは効果が薄れる。テストを見直す」（殺虫剤のパラドックス）
  - good「自動リグレッションは繰り返す価値がある」（副次解＝維持）
  - poor「繰り返すほど必ず新しい欠陥が見つかる」（明確な誤り）

**q4 限られた時間、どこを重点的に？**
- after：
  - best「欠陥は偏在する。集中している箇所を重点的に」（欠陥の偏在）
  - ★poor「新しく書いたコードだけを見れば十分」（惜しい＝新規は要注意だが"だけ"は偏在の誤読・既存の高リスク箇所も要る）
  - poor「どこも均等に薄くテストする」（明確な誤り）

### fl-1-04 テストの段取り 〜活動と役割〜

**q1 まず最初にやるべきことは？**
- after：
  - best「目的と範囲を定めるテスト計画から始める」
  - ★poor「テスト環境の構築から先に着手する」（惜しい＝実装活動で必要だが"最初"ではない・計画が先）
  - poor「いきなりテストケースを書き始める」（明確な誤り）

**q2 「何を」と「どうテストするか」の扱いは？**
- after：
  - best「分析で"何を"、設計で"どのように"を決める」
  - ★poor「設計で"何を"決め、分析で"どう"を決める」（混同＝分析と設計の役割が逆）
  - poor「分析と設計は区別せず進める」（明確な誤り）

**q3 テストの「役割」の理解は？**
- after：
  - best「テストする役割とマネジメントする役割がある」
  - ★good「テストする役割が中心だと理解する」（部分正答＝テスト実行役割は挙げたがマネジメント役割が抜ける）
  - poor「役割の区別はなく全部同じ」（明確な誤り）

**q4 テストウェアの扱いは？**
- after：
  - best「計画書・ケース・欠陥レポート等を構成管理する」
  - ★poor「テストケースと結果だけ管理すれば十分」（惜しい＝主要成果物だが計画書・条件・データ等も対象）
  - poor「成果物は使い捨てで管理は不要」（明確な誤り）

### fl-1-05 チームで品質をつくる 〜スキルと独立性〜

**q1 欠陥はどう伝える？**
- after：
  - best「事実ベースで建設的に伝える」
  - ★poor「重大な欠陥だけ口頭で手早く伝える」（惜しい＝迅速さは可だが記録に残らず再現情報も欠ける）
  - poor「作った人のミスとして責める言い方をする」（明確な誤り）

**q2 テストは誰がやるのがいい？（独立性）**
- after：
  - best「本人/同僚/別チーム/外部で独立性の度合いが違う」
  - ★good「別チームなど独立した人に任せるほどよい」（部分正答＝独立性は欠陥検出に有効だが、独立性が高いほど常に良いわけではない〔遅延・開発者の当事者意識低下等の弊害〕）
  - poor「独立性は不要、作った本人だけでよい」（明確な誤り）

**q3 品質は誰の責任？**
- after：
  - best「品質はチーム全員の責任（チーム全体アプローチ）」
  - ★poor「品質の最終責任はテストリーダーが負う」（惜しい＝役割はあるが"品質はチーム全員の責任"が原則）
  - poor「品質はテスターだけの責任」（明確な誤り）

## 【集計（改訂後・FL第1章）】
- 設問数 20（不変）。**全問3択化**（現状：2択12・3択8 → 改訂後：3択20）。
- rating分布：best 20／good 5（現状2→**5に増**）／poor 35。good比率 ≈11%（章内）。
- 各問に「惜しい誤答（部分正答・過剰・混同）」を最低1つ配置。FL方針どおり「明確な誤り」も各問1つ維持。

## 監修確認点
1. 難易度傾斜方針（FL=明確な誤りを1つ残す／AL=惜しい誤答2）の妥当性
2. 3択化（2択廃止）で validator「2〜3個」に収まる方針
3. good の付与基準（部分正答で限定的に正しいもの＝good）と増加（2→5）
4. 各かく乱肢がシラバス上「もっともらしいが誤り/不足」になっているか（20問×distractor）
5. best選択肢テキストの現状維持（正答は変えず、かく乱肢を足す/差し替える方針）

## 監修後の流れ
1. 承認 → JSON化（fl-1-01〜05 の choices を改訂・best/statusEffects/参照は原則不変、good追加分の statusEffects は配分ルール〔good=関連+1〜2〕）
2. 検証（validator 12項目・単体・E2E・実画面）→ PO実プレイ評価
3. 良ければ **skill（scenario-authoring）の評価基準・distractor設計を更新** → 全章（FL残り・AL-TM・AL-TTA）へ展開
