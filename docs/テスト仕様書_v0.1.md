## 1. テスト分析・設計の方針

### 1.1 テスト分析・設計のプロセス

テストケースを先に書かず、テスト分析（対象→アイテム→条件）→テスト設計（技法適用→全体俯瞰）の順で進める（test-spec.skill §1）。

```
【分析】STEP 1 テスト対象の識別 → STEP 2 テストアイテムへの分解 → STEP 3 テスト条件の導出
【設計】STEP 4 テスト技法の適用 → STEP 5 全体俯瞰・重複検出
```

### 1.2 テストケース表の読み方

```
テスト対象（FR単位）
└─ テストアイテム（FRを分解した単位）
   └─ 観点ID：テスト条件（何が成立すべきか）・適用技法
      └─ テストケース表（TC-ID・観点・実施主体・因子・水準・期待結果・合否基準）
```

- 観点ID形式：`FT-[FR番号3桁]-[連番3桁]`（例 FT-006-001）
- TC-ID形式：`[観点ID]-TC-[連番3桁]`（例 FT-006-001-TC-001）
- TC-IDから要件まで逆引き可能（FT-006-001-TC-001 → 観点 FT-006-001 → FR-006）

### 1.3 TC粒度の原則（実施主体に応じる）

| 実施主体 | 粒度 |
|---------|------|
| 人間テスト | 1 TC = 1 確認項目（1観点）。多軸検証は軸ごとに分割 |
| 自動テスト | 効率優先。spec内で `test()` を細かく分けるのは推奨 |

各テストケース表に「実施主体」列（自動／人間／どちらでも可）を設け、粒度判断の根拠とする。

**「実施主体」列の定義（v0.3 補足）：** **自動**＝自動テスト（計画書§10）で担保する見込み／**人間**＝手動でのみ確認する／**人間/自動**＝自動テストで担保しつつ人間も実施する（見た目・体感など自動で代替できない側面が残るもの）。各観点が具体的にどの自動テスト（単体Vitest／E2E／Lighthouse）で担保されるかは **§8 自動化カバレッジ一覧** に示す。実施主体列は「自動化が可能」を示すだけでなく、§8 と対で「自動化される計画がある／手動に残る」の証跡とする。

**重複観点の SKIP 可否も実施主体に依存する（本プロジェクトの原則）：**

- **自動テストTC**：複数FRに跨る重複観点は、重複排除のため SKIP（他TC参照）してよい。自動テストは網羅実行され、参照先が必ず実行されるため見落としが生じない（test-spec.skill STEP5 準拠）
- **人間テストTC**：重複していても SKIP せず、独立TCとして確認する。「他で見るからSKIP」という前提は人間テスターの見落としを生むため。1TC=1観点を維持し、その観点を実施面（どの画面で何を見るか）で具体化する。検証が他FRと重なる場合は、合否基準に役割分担（例：表示面から確認／集計はFR-Xで確認）を明記して重複の意図を残す

### 1.4 適用するテスト技法

| 技法 | 本書での主な適用先 |
|------|------------------|
| 同値分割 | ステータス加算値・選択肢数・テキスト長 |
| 境界値分析 | ステータス100クランプ（超過・ちょうど・上限到達後の加算）・テキスト200/400文字（有効/無効境界の両側）・選択肢2〜3・statusEffects 1〜5（有効境界）・初期値10 |
| デシジョンテーブル | タイトル画面の起動分岐（セーブ有無 × はじめから/つづきから） |
| 状態遷移テスト | 画面遷移（タイトル↔選択↔再生↔結果）・シーン送り（typing/done） |
| シナリオテスト | 新規プレイ・再開・再プレイの通しフロー |
| 異常値注入 | 壊れたシナリオJSON（検証12項目）・localStorage不可/破損 |
| エラー推測 | 数値露出（UI-RULE-006違反）・テキスト送り中の多重クリック・最終ノードでの分岐 |
| 背理法アプローチ | 数値非表示の証明（§4 FR-006で適用） |

### 1.5 背理法アプローチの適用箇所

「数値が画面に出ないこと」は正常系の直接確認が難しい（出ないことの証明）。背理法で設計する。

```
【背理法アプローチ】数値非表示（UI-RULE-006）
- バグシナリオ：実装が内部値を誤って描画したら、ステータス領域に数字（0〜100）や % が出現する
- 検出条件：ステータス領域のテキストに数字・% が観測されない
- 合否基準：status-bar-* 配下および結果画面の成長表示に数字・% が出ないこと（data-testid は設計書§10準拠）
```

内部値が正しく加算されていること自体は localStorage 直読（観測可能）で別途確認するため、「数値が出ない＝機能していない」の誤検出は起きない。

## 2. テスト対象外の個別判断

テスト計画書 §2.2 の基準を個別要件に適用した判断。

| 対象外項目 | 該当する基準 | 判断 |
|-----------|------------|------|
| エンディング判定・編成パターン・AL編・採用導線 | 未実装フェーズ | Phase 2〜4。本書では扱わない |
| URLディープリンク | 設計上の決定 | ルーター不採用（設計書§1）。リロードはタイトルへ戻る仕様で封じ |
| 実行時テキスト自動折り返し送り | 封じ済み低リスク | UI-RULE-002＋スキーマ検証#5（200文字上限）でデータ段階に封じ |
| 選択肢シャッフル | 封じ済み低リスク | UI-RULE-003で定義順固定 |
| サーバー側処理・個人情報漏洩 | 構成上の不在リスク | v1.0はバックエンド非保有・個人情報を保持しない設計 |
| ステータス減算 | 設計上の決定 | FR-006で減算なし。負方向の境界は存在しない（下限は初期値10からの単調増加） |
