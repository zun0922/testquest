## 1. テストの目的と基本方針

### 1.1 テストの目的

- Phase 1（MVP）が要件定義書 v1.0 の機能要件・非機能要件・受け入れ基準を満たすことを確認する
- 学習コンテンツ（シナリオデータ）が品質基準（正確性・整合性）を満たすことを確認する
- 社内パイロット・プレイテストに耐える品質で出荷可能かを判定する

### 1.2 基本方針

3本柱に基づく。

1. **テスト分析・設計を優先する** — 「何をテストするか」をテスト仕様書で構造化してから実施する
2. **要件とテストのトレーサビリティを確保する** — 全テストは要件（FR/AC/NFR）に紐付く（§5）
3. **リスクベースで優先度をつける** — リスクの高い箇所（採点に相当するステータス加算・数値非表示の担保・データ検証）を重点的にテストする（§9）

### 1.3 本プロジェクト固有の方針：コンテンツ品質テスト

本作はコードだけでなく学習コンテンツ（シナリオJSON）の品質が製品価値を決める。コードのテストと並行し、シナリオデータの品質を3層チェック（企画書13.2）で保証する。Layer 3（監修者によるサンプリング検証）を独立したテスト活動として計画に含める。

### 2.2 テスト対象外の基準

個別要件の対象外判断はテスト仕様書で行う。本計画では以下の基準で対象外を定める。

| 基準 | 本プロジェクトでの該当例 |
|------|------------------------|

| 構成上の不在リスク | サーバー側処理（v1.0はバックエンド非保有）・個人情報漏洩（個人情報を保持しない設計） |

## 3. テストの階層構造

下位層から上位層へ実施する。下位層がPASSしてから上位層へ進む。

```
Layer 1：単体テスト（AI・実装直後）
  対象：utils（validator/status/storage/scenarioLoader）・hooks（useTypewriter）の純ロジック
        ↓
Layer 2：機能テスト（人間・AIサポート・機能単位）
  対象：FR-001〜009 を画面操作で確認
        ↓
Layer 3：システムテスト（人間・AIサポート・全機能実装後）
  対象：通しシナリオ・状態遷移・パフォーマンス・構成・ユーザビリティ・回復性・セキュリティ
        ↓
Layer C：コンテンツ品質テスト（監修者・全シナリオ実装後）
  対象：FL第1章5本の技術的正確性・用語統一・シラバス項番整合（§4.9）
```

- Layer 1 と Layer C は他層と並行可能（Layer 1 はコード・Layer C はデータが対象のため）

## 4. テスト種別と目的

### AIサポートの定義

テストの実施（ブラウザ操作・目視確認・監修判断）は人間が行う。AIは以下のサポート業務を担う。本定義を全テスト種別に適用する。

- テストログCSV雛形の生成
- コマンドベースのテスト実施（`npm audit`・型チェック・Playwright E2E・Lighthouse CLI）
- 静的コードレビュー（XSS・型安全性・仕様準拠）
- FAILへの対応（原因分析・修正・再実装）
- テスト報告書の生成
- 機能テスト時の内部値確認（localStorage の読み出し提示・AC-006）

### 4.1 機能テスト

| 項目 | 内容 |
|------|------|
| 目的 | FR-001〜009 が仕様どおり動作することを機能単位で確認する |
| 担当 | 人間（実施）・AI（サポート） |
| タイミング | 各機能の実装・セルフレビュー完了後 |
| 合否基準 | 対応する全TC-IDがPASS |
| 参照 | テスト仕様書・テスト手順書 |

### 4.2 シナリオテスト（システム）

| 項目 | 内容 |
|------|------|
| 目的 | 「タイトル→章選択→シナリオ再生→選択→結果→再開」の一連フローが破綻なく完結することを確認する |
| 担当 | 人間（実施）・AI（サポート） |
| タイミング | 全機能実装後 |
| 合否基準 | 代表ユーザーフロー（新規プレイ・再開・再プレイ）が全てPASS |

### 4.3 遷移テスト（システム）

| 項目 | 内容 |
|------|------|
| 目的 | 要件10章の状態遷移図どおりに画面が遷移し、定義外の遷移が存在しないことを確認する |
| 担当 | 人間（実施）・AI（サポート） |
| 合否基準 | 全遷移トリガー（はじめから・つづきから・中断・分岐・戻る・リロード）が仕様どおり |

### 4.4 パフォーマンステスト（システム）

| 項目 | 内容 |
|------|------|
| 目的 | 要件7.1の性能基準（初期表示3秒・シーン遷移0.5秒・JSONロード2秒）を数値で確認する |
| 担当 | 人間（実施）・AI（Lighthouse CLI・計測サポート） |
| 合否基準 | 各指標が基準値内（計測は複数回の平均・最大を記録） |

### 4.5 構成テスト（システム）

| 項目 | 内容 |
|------|------|
| 目的 | 対応ブラウザ（Chrome・Edge・Safari最新版）・PC/スマホ縦での動作互換性を確認する |
| 担当 | 人間（実施）・AI（サポート） |
| 合否基準 | §8 のブラウザテスト戦略に従い、重点確認項目が全ブラウザでPASS |

### 4.6 ユーザビリティテスト（システム）

| 項目 | 内容 |
|------|------|
| 目的 | レスポンシブ（最小320px）・文字可読性・タップ領域44px・クリック/タップのみで操作完結（UI-RULE-005）を確認する |
| 担当 | 人間（実施・実機目視） |
| 合否基準 | スマホ実機でAC-011（縦画面でフロー完結）がPASS |

### 4.7 回復性テスト（システム）

| 項目 | 内容 |
|------|------|
| 目的 | エラー時の表示・回復が仕様どおりかを確認する（ロード失敗→エラー画面→再読み込み・保存失敗時の注記・localStorage不可環境） |
| 担当 | 人間（実施）・AI（異常データ・環境の準備サポート） |
| 合否基準 | AC-010（壊れたJSONで進捗破壊なし）を含む回復シナリオが全てPASS |

### 4.8 セキュリティテスト（システム）

| 項目 | 内容 |
|------|------|
| 目的 | XSS（シナリオテキスト・フィードバックの表示）・依存ライブラリ脆弱性のリスクがないことを確認する |
| 担当 | AI（`npm audit`・静的レビュー）・人間（確認） |
| 合否基準 | `npm audit` 高・中リスク0件・XSS確認項目が全PASS（要件7.3） |

### 4.9 コンテンツ品質テスト（Layer C・本プロジェクト固有）

| 項目 | 内容 |
|------|------|
| 目的 | FL第1章5本のシナリオが技術的に正確で、用語・シラバス項番が整合していることを確認する |
| 担当 | 人間（JSTQB有資格者＝監修者が実施）・AI（Layer 1自動チェック・指摘箇所の修正） |
| タイミング | 各シナリオJSON化後（Layer 1）／全5本実装後（Layer 3 監修） |
| 合否基準 | 全5本が監修承認済み（AC-012）・参照シラバス項番がFL V4.0 第1章の実在項番 |
| チェック観点 | (1) 選択肢の評価（最適/可/要改善）が技術的に妥当か、(2) フィードバック解説に誤りがないか、(3) シラバス項番が選択内容と対応するか、(4) 用語がISTQB用語集に準拠するか、(5) シラバス文章の転載がないか（著作権・要件8.3） |

## 6. テスト実施計画

### 6.1 実施フェーズと順序

```
[実装と並行] Layer 1 単体テスト（AI）：utils/hooks 実装ごと
       ↓
[機能単位]   Layer 2 機能テスト（人間）：FR完成ごと（6.2の順）
       ↓
[データ完成] Layer C コンテンツ品質テスト（監修者）：5本完成後
       ↓
[全完成後]   Layer 3 システムテスト（人間）：シナリオ→遷移→パフォーマンス→構成→ユーザビリティ→回復性→セキュリティ
       ↓
            テスト報告書（AI生成・人間承認）→ 出荷判定
```

### 6.2 機能テストの実施順序と依存関係

データロード・状態管理が他機能の基盤のため、下流から上流の順で確認する。

```
FR-009 データロード（基盤）
   ↓
FR-008 進捗保存（基盤）
   ↓
FR-001 タイトル → FR-002 章選択
   ↓
FR-003 再生 → FR-004 選択肢 → FR-005 フィードバック → FR-006 ステータス
   ↓
FR-007 結果表示（FR-006・FR-008に依存）
```

## 7. 合否判定基準

### 7.1 フェーズ別の合否基準（Phase 1 出荷判定）

開発フロー定義 §8 の必須条件に準拠する。

| # | 条件 |
|---|------|
| 1 | 全機能テスト（FR-001〜009 の全TC）がPASS |
| 2 | 全システムテストがPASS |
| 3 | P1不具合がOpen/Fixed状態で残っていない |
| 4 | パフォーマンス基準（7.1）を満たす |
| 5 | セキュリティ（npm audit 高・中0件・XSS全PASS）クリア |
| 6 | 受け入れ基準 AC-001〜012 を全て満たす |
| 7 | コンテンツ品質テスト：5本が監修承認済み（AC-012） |
| 8 | ドキュメントが最新版に整合（要件・設計・テスト計画/仕様/手順） |

### 7.2 不具合の重大度定義

開発フロー定義 §5 に準拠する。

| 重大度 | 本プロジェクトでの例 |
|--------|---------------------|
| Critical | ゲーム開始不可・シナリオが再生されない・進捗が保存されない |
| High | ステータス加算が誤る・分岐先が誤る・数値が画面に露出する（UI-RULE-006違反）・壊れたJSONで進捗が破壊される |
| Medium | 結果画面の表示順違い・グレーアウト漏れ・代替手段のある表示崩れ |
| Low | 軽微な余白ずれ・タイポ |

> 「数値の画面露出」を High に位置づける根拠：本作の中核設計判断（攻略的プレイの抑制・PO指摘で確立）に直接反する欠陥のため。

### 7.3 リリース判定基準

開発フロー定義 §8 の「条件付きリリースのリスクスコア（影響範囲×発生頻度×検知容易性）」を適用する。セキュリティ・コンテンツ正確性（監修）は本フレームワークの対象外とし、未達成なら無条件でリリース不可とする。


- `result`：PASS / FAIL / SKIP
- AIが `test_id`・`test_case`・`expected` を生成し、人間が `actual`・`result`・`notes` を記入する

### 8.4 構成テストのブラウザ戦略

| 確認レベル | 対象 | 選定基準 |
|-----------|------|---------|
| 重点確認（全ブラウザ） | レスポンシブレイアウト（本文200字の収容・§8.4設計）・localStorage動作・テキスト送り | CSSレイアウト・ブラウザAPI差異リスクが高い |
| 目視確認（主ブラウザのみ） | ボタン操作・画面遷移・グレーアウト | 標準的なDOM操作のみで差異リスクが低い |

## 9. リスクと対応策

| リスク | 種別 | 影響度 | テスト優先度への影響 | 対応策 |
|--------|------|--------|-------------------|--------|
| ステータス内部値の数値が画面に露出する | プロダクト | 高 | 数値非表示テストを最優先（5.4） | 全画面のステータス領域を機能テストで確認・E2Eで自動検証 |
| ステータス加算ロジックの誤り | プロダクト | 高 | 累積値テストを重点化 | localStorage直読で境界値（クランプ100・複数加算）を確認 |
| シナリオJSONの分岐欠陥（到達不能・行き止まり） | プロダクト | 高 | 検証#11/#12を必須テスト | validatorのスキーマ検証＋コンテンツ品質テストでルート網羅確認 |
| AI生成シナリオの技術的誤り | プロダクト・ビジネス | 高 | コンテンツ品質テストを出荷必須条件に | 監修者によるLayer 3検証・1本目で観点すり合わせ |
| シラバス文章の転載（著作権） | ビジネス | 高 | コンテンツ品質テストに転載チェックを含める | 監修観点(5)で全文確認・AIは概念から再構成 |
| AI生成コードのXSS考慮漏れ | プロジェクト | 中 | セキュリティテストを必須 | テキスト表示のエスケープを静的レビュー＋表示確認 |
| 監修工数の逼迫でテスト遅延 | プロジェクト | 中 | Layer Cを並行実施で前倒し | 5本完成を待たず、JSON化したものから順次監修依頼 |
| ブラウザ間のCSS差異 | プロダクト | 中 | 構成テストで重点確認（8.4） | レスポンシブを全ブラウザ確認・他は目視 |

## 10. 自動テスト計画

§4のテスト種別のうち自動化できるものを自動化し、人間の機能テスト・システムテストの負荷を継続的に下げる。手動テストを置き換えるのではなく、リグレッション防止と人間が確認すべき箇所への集中を目的とする。

### 10.1 テストピラミッドと本プロジェクトの方針

```
        E2E（Playwright）：少数・重要フロー
      ───────────────────────────
      単体テスト（Vitest）：多数・高速・純ロジック
```

本プロジェクトは **単体テスト＋E2Eの2層**を採用する。

> **クロスワードとの違い（重要）：** クロスワードはゲームロジックがUIと密結合していたためE2E中心・単体テストは将来送りだった。TestQuestは設計書§2・§6で**ロジックを純関数（`utils/`）に分離**している（validator・status・storage・scenarioLoader）。これらは入出力が明確で副作用がなく、単体テストの費用対効果が高い。したがって本作では単体テストを最初から第一層に位置づける。

### 10.2 目的別分類と実行頻度

| 目的 | 手段 | 実行頻度 |
|------|------|---------|
| ロジックの正確性保証（採点に相当） | 単体テスト（Vitest） | 実装ごと・push毎（CI） |
| リグレッション防止（主要フロー） | E2E（Playwright・ハッピーパス） | push毎（CI） |
| 数値非表示の担保（UI-RULE-006） | E2E（ステータス領域の数値非露出を検証） | push毎（CI） |
| データ品質の門番 | 単体テスト（validatorに全シナリオJSONを通す） | push毎・シナリオ追加時 |
| 視覚的退行防止 | VR（Visual Regression・任意） | UI変更時 |
| パフォーマンス監視 | Lighthouse CLI | 任意・システムテスト時 |

### 10.3 単体テスト（Vitest）の対象

| 対象モジュール | テスト内容 | 重点（リスク） |
|--------------|-----------|--------------|
| `utils/status.ts` | 加算・100クランプ・減算なし・複数キー同時加算・初期値10 | 高（採点に相当・§9） |
| `utils/validator.ts` | 検証ルール12項目（設計書§3.4）の正常系・各違反の検出・到達不能(警告)/行き止まり(エラー)の区別 | 高（データ品質の門番） |
| `utils/storage.ts` | save/load/clear・型ガード・不正データでnull・スキーマversion判定 | 中 |
| `utils/scenarioLoader.ts` | fetch成功/失敗・検証連携（fetchはモック） | 中 |
| `hooks/useTypewriter.ts` | 文字送り進行・全文即時表示の状態遷移 | 低 |

- **全シナリオJSONをvalidatorに通すテストを設ける**：`public/data/scenarios/` 配下の全ファイルを読み、検証エラー0件をCIで保証する（データ追加時の門番）

### 10.4 E2E（Playwright）の対象

設計書§10のdata-testid・`?skipTyping=1`・localStorage直読を用いる。

| E2Eシナリオ | 検証内容 | 対応 |
|------------|---------|------|
| 新規プレイ通し | はじめから→章選択→シナリオ→選択→フィードバック→結果→章選択 | AC-003〜007 |
| 進捗の保存と復元 | クリア後にリロード→つづきから→クリア状況・ステータス復元 | AC-008・FR-008 |
| ステータス内部値の検証 | 選択後にlocalStorageを読み加算値を確認（例 knowledge=13） | AC-006 |
| 数値非表示の検証 | `screen-play`/`status-bar-*` 配下に数値・%テキストが存在しない | UI-RULE-006・§5.4 |
| 再プレイ非加算 | クリア済みを再プレイ→localStorageのstatusが不変 | AC-009・FR-002 |
| 壊れたJSONの回復 | 不正シナリオ→エラー画面表示→localStorage非破壊 | AC-010・回復性テスト |
| 上書き確認 | セーブあり状態で「はじめから」→確認ダイアログ→キャンセルで進捗保持 | AC-002 |

実装パターンは Page Object Model・AAA・自動待機（`waitForTimeout`禁止）に従う。`beforeEach` でlocalStorageをリセットしテストの独立性を保つ。

> **分岐網羅の方針（v1.1・PO判断 A-2）：** E2E は代表ルート（王道＝ハッピーパス＋非王道 ST-SCN-001-TC-005）のみとし、全ルートのE2E化は行わない。シナリオの**全分岐の網羅性は validator 検証#11（全ノード到達可・行き止まりなし）で構造的に担保**する。全ルートのE2E化は **Phase 2 の自動化計画で必要に応じて検討**する（現時点では過剰と判断）。

### 10.5 自動化の対象外（手動に残す）

| 対象 | 手動に残す理由 |
|------|--------------|
| コンテンツの技術的正確性（評価・解説の妥当性） | 意味の正しさは監修者の判断が必要（Layer C・自動化不能） |
| 立ち絵・背景・メーターの見た目の印象 | 視覚的な印象評価は人間の目視 |
| スマホ実機でのフロー完結（AC-011） | 実機固有の挙動・タップ感はエミュレータで代替不可 |
| テキスト送りアニメーションの体感 | タイミング依存・体感品質は人間が確認 |

### 10.6 CI連携

- GitHub Actions（クロスワードの `playwright.yml` 構成を踏襲）で push・pull_request 時に実行
- ジョブ：`npm ci` → 型チェック（`tsc --noEmit`）→ `npm audit` → 単体テスト（Vitest）→ E2E（Playwright・ヘッドレス）
- CI安定化：E2Eは `retries: 2`・失敗時にスクリーンショット/動画保存・並列実行
- localhost実行を基本とし、Vercel確認は `deploy-before-test.md`（push→デプロイ完了確認→テスト）に従う

### 10.7 自動化率の目標（Phase 1）

| 区分 | 目標 |
|------|------|
| 単体テスト：utils の分岐網羅 | ステートメントカバレッジ80%以上（status・validatorは90%以上） |
| E2E：受け入れ基準の自動化率 | **AC-001〜010 の全10項目をE2E化**（AC-011実機・AC-012監修は対象外）。実装で AC-001〜010 すべてのE2Eを確認済み（v1.1で「8項目」から確定） |
| 数値非表示（UI-RULE-006） | 全プレイ画面でE2E自動検証 |

> 自動化率は「手動テストを減らす」ためでなく「リグレッションを機械で止める」ための指標。カバレッジ数値の達成自体を目的化しない。
