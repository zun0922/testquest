## ⚠️ 出力ファイルの保存先（重要・必ず先に確認）

Cowork でスライド画像・pptx を生成したら、**必ず以下の保存先にダウンロードしてください**。

| 出力ファイル種別 | 保存先 | 命名例 |
|---------------|--------|--------|
| PowerPoint（.pptx） | `C:\dev\testquest\presentations\` | `TestQuest_MVP総括_v1.0.pptx` |
| スライド画像（.png / .jpg） | `C:\dev\testquest\slides\v1.0\` | `v1.0_slide-01.png` 〜 `v1.0_slide-09.png` |
| 差分版・修正版の画像 | `C:\dev\testquest\slides\v1.0b\` | `v1.0b_slide-XX.png`（b/c/d で版分離） |

**プロジェクトルート直下（`C:\dev\testquest\` 直下）・`docs\` 直下には絶対に保存しないでください。**

> **過去事例（同じツールで2回発生）：** クロスワードプロジェクトで Cowork 生成物（スライド画像18枚＋pptx）が
> 親フォルダ直下に散乱する事故が **2026-05-16 と 2026-05-19 の2回**発生した。
> 教訓＝**「skill を新設しただけでは再発しない。依頼パッケージとプロンプト自体に保存先を埋め込む必要がある」**
> **「AI Code から外部ツールの保存先は制御できない」**。本セクションがその予防策（3層構造の層1）。
>
> 詳細：`skills/configuration-management.skill` §7.5 ／ 出力先の規約は `CLAUDE.md` §7 に事前定義済み（層3）

## 📋 使い方（3ステップ）

### Step 1：Cowork セッション開始

Claude Cowork で新規スライド生成セッションを開始する。
**事前に上記「出力ファイルの保存先」を確認してください。**

### Step 2：添付ファイルをアップロード

#### zip 一式を1ファイル添付（**全部入り・777KB・8ファイル**）

```
presentations/Cowork用_MVP総括一式_v1.0.zip   ← これ1件で完結
├── Cowork用_スライド生成パッケージ_v1.0.md   （本パッケージ）
├── MVP完了報告書_v0.1.md                     （★数値の正）
├── MVP総括スライド_ブリーフ_v0.1.md          （★構成9枚・PO確定事項）
├── 企画書_TestQuest_v1.2.md                  （企画の狙い・対象・ルート構成）
├── 開発フロー_役割分担定義_v0.1.md           （役割分担・制作フロー3系統＝4枚目/6枚目の根拠）
├── 宿題リスト_v1.0.md                        （残課題・保留判断＝7枚目/8枚目の根拠）
└── screens/                                  （スライド2で使う実画面）
    ├── play-feedback.png                     （プレイ中：立ち絵＋評価フィードバック）
    └── select-chapters.png                   （章選択：折り畳み・進捗表示）
```

> **Cowork が全部を読み切れない場合**は、★印の2件＋本パッケージ＋画像2枚（計5点）に絞って再添付してください。
> 9枚を書くのに必要な情報はその5点で足ります（不足分は本ファイルの「📦 プロジェクトコンテキスト要約」が補います）。
> zip 自動展開に対応していない場合も同様に個別添付で進められます。

**zip は gitignore 対象（再生成可能）。** 作り直す場合：

```powershell
# 一時ディレクトリへ材料を集めて再圧縮する
$stage = "$env:TEMP\coworkpkg"; New-Item -ItemType Directory -Force "$stage\screens" | Out-Null
Copy-Item docs\Cowork用_スライド生成パッケージ_v1.0.md,docs\MVP完了報告書_v0.1.md,docs\MVP総括スライド_ブリーフ_v0.1.md $stage -Force
Copy-Item 企画書_TestQuest_v1.2.md,docs\開発フロー_役割分担定義_v0.1.md,docs\宿題リスト_v1.0.md $stage -Force
Copy-Item e2e-shots\04-feedback.png "$stage\screens\play-feedback.png" -Force
Copy-Item e2e-shots\06-select-collapsed.png "$stage\screens\select-chapters.png" -Force
Compress-Archive "$stage\*" presentations\Cowork用_MVP総括一式_v1.0.zip -Force
```

※ 画面イメージは `e2e-shots/`（E2E実行で生成される・gitignore対象）から取る。無い場合は `npm run test:e2e` を実行すれば再生成される。

## 🎯 メインプロンプト（コピペ用）

```
添付した資料（MVP完了報告書 v1.0 ＋ MVP総括スライド_ブリーフ v0.2 ＋ 実画面2枚）を元に、
TestQuest（JSTQBテストエンジニア育成ゲーム）の MVP完了総括スライドを
「9枚ちょうど」で作成してください。

【目的】
- MVP（Phase 1）完了の成果を社内共有する
- 対象読者：経営層＋社内メンバー（非エンジニアを含む）
- トーン：技術詳細よりも「何ができるようになったか」「組織として何が資産になったか」「次に何を狙うか」
- 専門用語（受け入れ基準・validator・門番テスト 等）を使う場合は一言の補足を添える

【重要な前提】
このプロジェクトはクロスワードゲームに続く「2つ目」のプロジェクトです。
したがって総括の芯は「学習ゲームが1本できた」ではなく
**「クロスワードで確立したAI駆動開発の方法論を、題材の違う別プロジェクトで実装し、
再現できた」** ことです（PO確定方針）。

【スライド構成（9枚ちょうど・1枚1メッセージ）】
各スライドのタイトルは「メッセージそのもの」にしてください（「実績」ではなく
「約2.3か月で企画から出荷判定まで完走」のように）。

1. 表紙：TestQuest はMVP完了・本番稼働中。2つ目のプロジェクトで方法論を実装した
2. 何を作ったか：JSTQBの学習を「読む」から「判断して選ぶ」体験に変えた学習ゲーム
   （3ルート＝入門/マネジメント/テクニカル。添付の実画面2枚を配置）
3. 実績（数字1枚）：約2.3か月で企画から出荷判定まで完走
   （シナリオ71本・決定ポイント280問・参照シラバス項番151・全71本が全数監修）
4. 【主題】方法論の実装：クロスワードの方法論を別ドメインへ移植して機能した
   （移植できたもの／作り足したものを対比で見せる）
5. 品質の仕組み：AIに任せても破綻しない3点セット
   （データ品質門番・全数監修・本番スモーク／単体177件＋E2E15件・脆弱性0件）
6. 人間とAIの役割：人間は「決める人」に集中し、AIが作る・試す・記録する
7. 正直な限界：できていないことも開示する
   （手動テスト102項目は未実施／モバイル要件は仕様変更／法務確認は待ち。
    代替手段と再開の道筋を同じスライドに併記して、次の8枚目へつなぐ）
8. 展望：次は学習効果の可視化と対象拡大
   （進捗のクラウド保存・定着度の扱い／問題文の磨き込み／社内パイロット→対象拡大）
9. まとめ：要点3行
   （①方法論は移植できる ②品質は仕組みで担保できる ③人間の仕事は「決める」に寄る）

【特に強調すべきメッセージ（必須・4点）】

1. **「方法論の実装」**（最重要・4枚目に1枚以上を充てる）
   クロスワードで作った開発フロー・スキル資産・ルール体系を、題材の異なる
   TestQuest へ移植したら機能した。
   - 移植できたもの：開発フロー6STEP／要件・設計・テスト系スキル／
     .claude/rules の二層構造／worklog と宿題リストによる中断・再開／セルフレビュー5観点
   - 作り足したもの：シナリオ制作の方法論（scenario-authoring）／
     AI画像制作の方法論（image-asset-production）／
     開発フロー定義のTestQuest版（コンテンツ制作フロー3系統を新設）
   → 「2つ目で速くなった」ことが再利用性の証拠。1つ目との違いを対比で示す。

2. **「AIに任せても破綻しない品質の仕組み」**
   - データ品質門番：全71本のシナリオに対し、検証12項目＋本数＋項番規約を
     コード変更のたびに自動チェック（学習コンテンツをコードと同じ厳しさで守る）
   - 全数監修：71本すべてを人間が承認（抜き取りではない）
   - 本番スモーク：公開後に配信データを全数検証してから完了とする

3. **「人間の役割は『決める』に寄った」**
   人間＝要件決定・監修承認・画像採用・公開判断／AI＝実装・テスト・記録・是正。
   人間が手を動かす場面が減り、判断に集中する形になった。

4. **「正直な限界を開示する」**（7枚目）
   手動テスト102項目は未実施（自動テスト＋全数監修＋通しプレイで代替）／
   モバイルは縦画面対応から横持ち前提へ仕様変更／画像生成の法務確認は結果待ち。
   **隠さずに書き、それぞれの代替手段と再開の道筋を併記する。**
   「できていないことを把握できている」ことを強みとして示す。

【スタイル】
- 1スライド1メッセージ（本文は最小限。補足数値は必ずノート欄へ）
- 表・矩形図・矢印図を多用し、テキストの羅列は避ける
- 4枚目（方法論の実装）は「移植できたもの／作り足したもの」の対比図
- 5枚目（品質の仕組み）は3点セットの図解
- 6枚目（役割）は人間とAIの2列対比
- 配色は下記「デザイン仕様」に従う（アプリ画面と同じ世界観にする）

【期待する出力】
- スライド9枚分のタイトル・本文・話す原稿（ノート欄）
- 各スライドの図解・配置の指示
- 数値は添付のMVP完了報告書から引く（概算や推測で書かない）
```

### フォント

`Segoe UI` → `Hiragino Sans` → `Meiryo` → sans-serif（アプリと同じ指定）。

### レイアウト原則

- 1スライド1メッセージ。**タイトルがメッセージ**
- 本文は箇条書き3〜5行まで。**それ以上はノート欄へ**
- 数字は大きく見せる（4枚目・5枚目の主要指標）
- 図解優先：対比は2列、プロセスは矢印、分類は矩形
- 7枚目（限界）は赤系を使うが**ネガティブに見せない**（限界→代替→再開の3列で前向きに）
