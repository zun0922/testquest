## 1. 背景：企画書の条件が機能しない

### 1.1 企画書 §7.2 の条件

| エンディング | 条件 |
|-------------|------|
| 知識の探求者 | 知識が最高値 |
| テスト職人 | スキルが最高値 |
| チームの要 | チームワークが最高値 |
| 隠しEND：最高のQAエンジニア | 全ステータス70以上 |

### 1.2 実測（FL編クリア時点のステータス）

| プレイ | 知識 | スキル | 自信 | チームワーク | 企画書条件での判定 |
|--------|------|--------|------|-------------|------------------|
| 全問 best | **100** | 100 | 100 | **66** | 最高値が3つ同点／隠しEND**不成立** |
| best/poor交互 | **100** | 80 | 64 | 35 | 知識の探求者 |
| 3問に1問best | **100** | 57 | 46 | 29 | 知識の探求者 |
| **全問 poor** | **100** | 10 | 10 | 10 | **知識の探求者** |

**どのプレイでも知識が100に張り付き、全問 poor ですら「知識の探求者」**になる。
**隠しEND はどのプレイでも達成できない**（チームワークが最大66）。

### 1.3 原因：加算量の偏り

| ステータス | 合計加算（全71本） | 出現回数 |
|-----------|------------------|---------|
| 知識 | 901（45%） | 738回 |
| スキル | 651（33%） | 273回 |
| 自信 | 284（14%） | 280回 |
| チームワーク | **166（8%）** | **84回** |

決定的なのは **poor 選択肢の加算の89%が知識**であること。企画書 §7.1 の「不正解でも学びがあるためゼロ成長にしない」という設計意図が知識に集中し、**選ばなくても知識だけが伸び続ける**構造になっている。

このままではKPI「**複数エンディング到達率30%以上**」（企画書 §14）も達成できない。

## 2. 判定方式（PO決定 2026-08-30：達成率方式）

### 2.1 達成率

```
達成率(k) = 正解して得た k の累積 ÷ 理論最大(k)

  正解して得た k の累積 : best / good を選んだときの statusEffects(k) の合計
                          （poor で得た分は算入しない）
  理論最大(k)           : 各問で best / good のうち k の加算が最大のものを
                          選んだ場合の合計（FL編で 知識202・スキル134・自信108・チームワーク56）
```

**poor で得た分を除外する**のが要点。これを入れると知識が常に突出し、どんな判定方式でも分岐しない（§1.3）。
「**正解して伸ばした分だけが実力**」という解釈で、学習教材として筋も通る。

### 2.2 判定ロジック

1. 知識・スキル・チームワークの3つの達成率を求める
2. **最大 − 最小 < 8ポイント** → **隠しEND「最高のQAエンジニア」**（バランス型）
3. そうでなければ**最高の達成率**のステータスに対応するエンディング
4. 同点の場合は 知識 → スキル → チームワーク の順で決定的に選ぶ（再現性のため）

> **自信（confidence）は判定に使わない**。企画書 §7.2 に対応するエンディングが無いため。
> 自信は best 選択肢にしか加算されない（good/poor は0）ので、「自信が高い＝最適解を選び続けた」を意味し、
> 結果としてバランス型（隠しEND）に現れる。

### 2.3 検証結果（gap=8）

| プレイ | 知識 | スキル | 自信 | チームワーク | 判定 |
|--------|------|--------|------|-------------|------|
| 全問 best | 100 | 100 | 100 | 100 | **隠しEND** |
| 全問 good | 81 | 90 | 68 | 75 | テスト職人 |
| 知識重視 | 100 | 93 | 96 | 89 | **知識の探求者** |
| スキル重視 | 93 | 100 | 95 | 100 | 隠しEND |
| チームワーク重視 | 92 | 99 | 94 | 100 | **チームの要** |
| ランダム#1〜#8 | — | — | — | — | 知識2／チーム3／テスト職人1／隠し1／その他1 |

**4種すべてに到達可能**で、現実的なプレイ（ランダム8件）も分散する。
gap=15 にすると隠しENDが10/15件と偏るため、**8ポイントを採用**する。

> **未決事項①**：gap=8 の妥当性。実プレイのデータが貯まったら再調整の余地がある。

## 3. データ設計

### 3.1 `SaveData` の拡張

#### `ClearRecord` に判定用の累積を追加

```jsonc
{
  "clearedAt": "2026-08-30T...",
  "ratings": { "best": 3, "good": 1, "poor": 0 },
  "statusGain": { "knowledge": 8, "skill": 5 },      // 既存（poor 含む・表示用）
  "cleanGain":  { "knowledge": 8, "skill": 5 }       // 追加（poor 除く・判定用／省略可）
}
```

- **省略可**とし、既存のセーブデータ（`cleanGain` なし）でも壊れないようにする
- 既存プレイヤーは、再プレイまたは未クリア章のクリアで順次貯まる
- `SaveData` の `version` は 1 のまま（フィールド追加のみで後方互換）

**既存プレイヤーの扱い（PO決定 2026-08-30）**：`cleanGain` が**無い章は判定から除外**する。
`statusGain` で代用すると poor 由来の知識が混ざり、§1.3 の偏りをそのまま持ち込むことになるため。
未記録の章がある人は、その章を再プレイすれば記録される（再プレイでもステータスは加算されないが、`cleanGain` の記録は行う）。

#### 到達したエンディングの記録

```jsonc
{
  "version": 1,
  "status": { ... },
  "cleared": { ... },
  "endings": { "fl-balanced": "2026-08-30T12:00:00.000Z" }   // 追加（省略可）
}
```

- **省略可**。既存セーブは空として扱う
- 一度到達したら消えない（再プレイで別のエンディングに到達すると**追加**される＝コレクション要素）

### 3.2 エンディングの定義（全7種・PO決定 2026-08-30）

| # | ID | 到達条件 | 名称 | 描かれる姿 |
|---|----|---------|------|-----------|
| 1 | `fl-knowledge` | FL全27本クリア＋知識が最高 | 知識の探求者 | JSTQB Foundation Level 合格への道 |
| 2 | `fl-skill` | FL全27本クリア＋スキルが最高 | テスト職人 | 現場で信頼されるテスト設計のスペシャリスト |
| 3 | `fl-teamwork` | FL全27本クリア＋チームワークが最高 | チームの要 | QA文化をチームに根付かせるリーダー |
| 4 | `fl-balanced` | FL全27本クリア＋3ステータスの差が8ポイント未満 | 最高のQAエンジニア（隠し） | 完全なテストエンジニア像 |
| 5 | `al-tm` | AL-TM 全23本クリア | マネジメントルート達成 | テストマネージャーへの道 |
| 6 | `al-tta` | AL-TTA 全21本クリア | 技術スペシャリストルート達成 | テクニカルテストアナリストへの道 |
| 7 | `grand` | 5と6の両方に到達 | 最終エンディング | 両の道を修めた者 |

- **FL編（1〜4）はステータス分岐**（§2.2）。**AL編（5〜6）はルート固定**で、企画書 §7.2 の「それぞれのクリア演出」に対応する
- **7 は5と6の両方を満たしたときに解放**される（企画書 §7.2「両ルート制覇で最終エンディング」）

### 3.3 既存の最終回演出との関係（重複を避ける）

AL編の各ルートには、**シナリオ内に既にクリア演出がある**。

| シナリオ | 既存の締めくくり |
|---------|----------------|
| `al-tm-3-04` | 田中課長「……もう立派なテストマネージャー候補だ。次の経営会議、隣の席は空けておく。」 |
| `al-tta-6-03` | 匠「……いってこい、テクニカルテストアナリスト。」 |
| `fl-6-02` | ケンの章の締め（**FL編全体の締めくくりではない**） |

したがってエンディング画面は、**シナリオの締めくくりの「その先」を描く**ものとして書き分ける。
既存の ending ノードと同じ内容を繰り返さない。

### 3.4 判定タイミング

**結果画面の「戻る」操作**のタイミングで到達条件を評価し、条件を満たしていればエンディング画面へ遷移する。
同時に複数到達した場合（AL-TTA クリアで `al-tta` と `grand` が同時など）は**全件を記録し、表示は1つ**（最終エンディングを優先）。
残りは一覧から見られる（§4.2）。

## 4. UI

### 4.1 エンディング画面（再生）

| 項目 | 仕様 |
|------|------|
| 遷移 | **結果画面の「戻る」を押したとき**に到達条件を評価し、満たしていればエンディングへ（結果を飛ばして唐突に遷移しないため） |
| 表示 | エンディング名・描かれる姿・本文（複数行を順に送る） |
| 演出 | 背景＋立ち絵＋テキスト送り。**既存の `useTypewriter` を流用**する |
| 数値 | **一切表示しない**（UI-RULE-006）。達成率のパーセンテージは出さない |
| 終了 | 「タイトルへ」または「章選択へ」で抜ける |

### 4.2 エンディング一覧（PO決定 2026-08-30）

| 項目 | 仕様 |
|------|------|
| 入口 | **章選択画面のみ**（到達が1件以上あるときだけボタンを出す）。タイトル画面は「はじめから／つづきから」の2択のまま保つ（設計書 §5.1） |
| 一覧 | 全7種を定義順に表示。**到達済みは名称と到達日、未到達は「？？？」**で伏せる |
| リプレイ | 到達済みの項目を選ぶと、そのエンディングを再生する |
| 進捗表示 | 「n / 7」の到達数を表示（**エンディングの数え上げは数値表示の対象外**＝ステータスではないため UI-RULE-006 に抵触しない） |

> 未到達を伏せることでリプレイ動機になる。KPI「複数エンディング到達率30%以上」（企画書 §14）への寄与を狙う。

## 5. 受け入れ基準（案）

| AC | 基準 |
|----|------|
| AC-P2-002-1 | FL編の全27本をクリアするとエンディング画面に到達する |
| AC-P2-002-2 | 判定は `cleanGain`（poor を除く累積）の達成率で行う |
| AC-P2-002-3 | 3ステータスの達成率の差が8ポイント未満なら隠しENDになる |
| AC-P2-002-4 | 同じセーブデータからは常に同じエンディングになる（判定が決定的である） |
| AC-P2-002-5 | エンディング画面に数値・%が表示されない（UI-RULE-006） |
| AC-P2-002-6 | `cleanGain` が無い既存セーブでもエラーにならない（**無い章は判定から除外**される） |
| AC-P2-002-7 | AL-TM／AL-TTA を全クリアするとそれぞれのエンディングに到達し、**両方に到達すると最終エンディングが解放**される |
| AC-P2-002-8 | エンディング一覧で、**到達済みは名称が見え、未到達は伏せられる** |
| AC-P2-002-9 | 一覧から到達済みのエンディングを再生できる |
